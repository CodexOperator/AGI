## Summary

- Blog: "320B total parameters and only 18B active parameters"; "first natively multimodal model in the GLM-5 family"; trained on "our latest 30T-token multimodal corpus"; served anonymously as "Ox Alpha" with "all traffic served on Chinese AI accelerators".
- Blog, vs GLM-4.5 (similar total size): "reduces the number of active parameters from 32B to 18B and the number of layers from 92 to 45".
- Blog: hybrid attention — "Linear attention captures local dependencies through state modeling, while sparse attention uses a lightweight indexer to retrieve relevant information from the global context"; at up to 1M context "IndexPool further reduces indexer latency and memory overhead by compressing four cached key vectors into one through weighted pooling".
- Blog, vs GLM-5.3: "a 3.0x reduction in attention compute" and "a 4.4x reduction in KV-cache size"; "lowest attention compute among the models included in our comparison", but KV footprint "slightly larger than that of some comparable Flash-class models".
- Blog, serving stack: "intra-node tensor parallelism, ReplaySSM, W8A8 quantization, hybrid INT8/FP8/BF16 cache quantization, Layer Split, and an Encode-Prefill-Decode disaggregated architecture" -> "a threefold improvement in end-to-end serving performance compared with our initial baseline on the same hardware". The blog's own caveat: the efficiency comes from "the combined design ... not from any single technique".
- config.json makes the layer map concrete: 45 layers = 34 `linear_attention` (KDA, 64 heads x 128 dim, short_conv_kernel_size 4) + 11 `deepseek_sparse_attention` at layers [3,7,11,...,43] (every 4th); indexer `index_n_heads 32`, `index_head_dim 128`, `index_topk 2048`, `index_kpool 4` (the IndexPool); MoE `n_routed_experts 288`, `num_experts_per_tok 8`, `n_shared_experts 1`, `moe_intermediate_size 2048`, `first_k_dense_replace 3`; `mhc: true`, `hc_mult 4`, `hc_sinkhorn_iters 20`; `kv_lora_rank 512`, `qk_head_dim 256`, `qk_rope_head_dim 0` (`mla_use_nope: true`); `num_nextn_predict_layers 1` (MTP); shipped as FP8 e4m3 block-128 weights.
- GLM-5 report (the linked report), the compute tricks with numbers: DSA "reduces the attention computation by roughly 1.5-2x for long sequences" (Sec 2.1.1); DSA adaptation on GLM-5 used "1000 steps ... 14 sequences of 202,752 tokens" warm-up then "20B tokens" sparse adaptation vs DeepSeek-V3.2's "943.7B tokens"; DSA on GLM-4.7-Flash with the indexer-only warm-up ("1,000 steps (batch size 16)", base frozen) keeps RULER 4K-64K within ~1.3 points and drops 128K "79.21 -> 71.35"; the full 150B-token joint phase recovers to 78.86 (Table 6).
- GLM-5 report Table 4 (zero additional training, GLM-9B, 1:1 full:SWA, 4096-token window): naive SWA interleave collapses RULER@16K 92.01 -> 25.89, while a beam-searched layer pattern (found at 16K only) holds 88.92 at 16K and 53.95 at 128K; Table 5 (190B continual tokens): SimpleGDN (linear recurrence built from the pre-trained Q/K/V weights, no conv, no gate) is -3.59/-8.25 on RULER@64K/128K and +2.12/+4.48 on HELMET-ICL vs the full-attention baseline.
- GLM-5 report Sec 2.1: MLA head dim raised 192 -> 256 with heads cut by 1/3 "keeps the training computation and the number of parameters constant while decreasing the decoding computation"; 3 MTP layers share parameters during training -> accept length 2.76 vs DeepSeek-V3.2's 2.55 at 4 speculative steps (Table 2).

## Relevance to local-maxxing

The blog is a product page — every headline number is relative to Z.ai's own models and none of it runs on the town's iron (320B FP8 does not fit 23 GB or 8 GB; the swarm box's frame is bytes-per-token at 0.6B-4B). What transfers is the *shape* of the savings: (1) the 3:1 linear:sparse layer ratio (34 KDA + 11 DSA of 45) is the current best-known recipe for making attention bytes/token ~constant in context length, and on the bandwidth-bound swarm box the KV cache — not the weights — is what grows the bytes read per decoded token at long context; (2) the GLM-5 report's Table 4 shows a *zero-training* layer-selection trick (beam-searched sliding-window pattern on half the layers, 88.92 vs 92.01 RULER@16K, while a naive interleave dies at 25.89) — exactly the kind of experiment the town can run on Qwen2.5-0.5B on local-town, and it is the same "per-layer importance is not uniform, the global proxy anti-predicts" finding D1 already measured for mean-ablation; (3) DSA's indexer-only warm-up (base frozen, 1,000 steps) is the cheapest published route to token-level sparsity and its indexer (score -> ReLU -> top-k, 32 heads x 128 dim) is a small enough side network to be the first candidate for an E3 byte-neuron/LUT replacement — a top-k selector is a threshold, and a threshold crossing is a flip. Layered with the looped transformer, a shared indexer across loop iterations (`index_share_for_mtp_iteration: true` is the same idea applied to MTP) would keep the selection bytes constant per loop.

## Idea seed

- slug: lm-searched-swa-pattern-zero-train
- title: Beam-search a per-layer sliding-window pattern, no training, to cut long-context KV bytes/token
- lever: Replace full attention with a 1K-4K sliding window on a searched half of the layers (GLM-5 Table 4: searched pattern keeps RULER@16K 88.92 vs 92.01 full, naive interleave 25.89) so that half the layers read only window/context of their KV cache per decoded token — at 16K context that is ~37% fewer KV bytes read per token with zero training and zero weight changes.
- buys: A drop-in decode-bandwidth win on the swarm box for the long-context kids (the KV read exceeds the Q8 weight read once context passes a few thousand tokens for a 0.6B model), and a per-layer "which layers can be windowed" map that can be compared head-to-head with D1's per-layer mean-ablation importance — if the two rankings agree, one measurement buys both levers.
- first_falsifier: On Qwen2.5-0.5B with half the layers windowed at 1K on 8K-context needle/RULER-lite prompts, if NO searched pattern (beam 4, 2 layers/step) stays within 5 points of full attention while the naive interleave collapses, the layer-selection lever does not exist at 0.5B scale and the idea dies.
- cheapest_test_on_our_iron: local-town (gpu-8g) with HF transformers eager attention and a per-layer window mask on Qwen2.5-0.5B bf16 at 8K context — ~50 RULER-lite prompts per candidate, beam 4, ~12 search steps, roughly 3-6 GPU hours, $0; then port the winning pattern's KV-read delta to a tg tok/s measurement at 8K context on the swarm box.

## Critique (adversarial, 2026-09-16)

Re-fetched every source with `curl -sL -A 'Mozilla/5.0'` (blog 200/33,531 B; HF README 200/8,027 B; config.json 200/69,416 B; arXiv 2602.15763 PDF 200/6,177,650 B, 40 pp, 2,330 pdftotext lines; abs 200/72,031 B) — byte counts identical to the reader's. Every number in the Numbers section was located in the fetched bytes (blog text, config.json keys, report Sec 2.1/2.1.1/2.1.2, Tables 2/4/5/6/10). Grounded 4/5: the digest is accurate on the sources; the errors are in the reader's glosses and in the idea seed's own arithmetic and cost estimate.

**Errors / corrections**

1. Summary line "DSA on GLM-4.7-Flash with the indexer-only warm-up ... keeps RULER 4K-64K within ~1.3 points" — wrong. Table 6 deltas (warmup − base) are +0.07 / −0.18 / −0.43 / **−2.87 (32K)** / −1.29 / −7.86. The 32K drop is 2.87, so "within ~1.3" holds only for 4K–16K and 64K. Correction: "within 0.5 pts at 4K–16K, −2.87 at 32K, −1.29 at 64K, −7.86 at 128K".
2. Relevance: "the 3:1 linear:sparse layer ratio ... is the current best-known recipe for making attention bytes/token ~constant in context length" — the reader's claim, not the source's. The blog says only "3.0× reduction in attention compute" and "4.4× reduction in KV-cache size" vs GLM-5.3 and explicitly that the KV footprint "remains slightly larger than that of some comparable Flash-class models". Mechanically the DSA layers are *not* constant in context: the indexer still scores every (pooled, `index_kpool=4`) key — O(L/4) per token — and then reads `index_topk=2048` entries; only the 34 KDA layers are constant-state. "Best-known" is unsupported anywhere.
3. Relevance: "the indexer ... is the natural first candidate for an E3 byte-neuron/LUT replacement ... a threshold crossing is a flip" and "the same ... finding D1 already measured" — reader's speculation stitched to town threads; the report says only that the searched pattern works "by preserving full attention where it matters most" (Sec 2.1.2) and that the Lightning Indexer kernel "integrates score calculation, ReLU, and TopK" (Sec on Ascend kernels, ~L1271). Keep as a town hypothesis, not as something the source supports.
4. Idea lever: "~37% fewer KV bytes read per token at 16K" — not in the source. The report measures **RULER accuracy only** for the SWA pattern (Table 4/5); it reports no throughput, bytes or latency for it. 37% is the reader's arithmetic (0.5 + 0.5·4096/16384 = 0.625 of full KV reads) and is correct only for a 4K window at 16K; the lever text says "1K-4K", and at 1K/8K the figure is 43.75%, at 2K/8K 37.5%. Mark as derived, not measured.
5. Idea lever: the cost of the search itself is unreported by the source and non-trivial — beam 8, 2 layers/step, ~10 steps on a 40-layer 9B model means thousands of candidate RULER@16K evaluations (step 1 alone is C(40,2)=780). "Zero training" is true; "zero cost" is not.
6. Idea buys / falsifier mismatch: "the KV read exceeds the Q8 weight read once context passes a few thousand tokens for a 0.6B model" holds for **Qwen3-0.6B** (config.json: 28 layers × 8 KV heads × head_dim 128 → 114,688 B/token f16 KV; ≈940 MB at 8K, crossover with a ~0.6 GB Q8 weight read near ~5K tokens). It does **not** hold for the falsifier's model **Qwen2.5-0.5B** (config.json: 24 layers × 2 KV heads × 64 dim → 12,288 B/token; ≈100 MB at 8K, ~17% of bytes/token next to ~0.5 GB of Q8 weights) — windowing half its layers at 8K saves ~6% of bytes/token. The accuracy test and the bandwidth claim are on different models; run both halves on Qwen3-0.6B, which is also the swarm box's measured model (tg 34–45 tok/s).
7. Idea cheapest test: "beam 4, ~12 search steps, ~50 prompts per candidate, 3-6 GPU hours" does not add up. Halving a 24-layer model at 2 layers/step is 6 steps (7 for 28 layers), not 12; beam 4 × 2 layers/step over 24 layers is ~3,400 candidate evaluations × 50 prompts ≈ 170,000 8K-context forwards — not 3–6 hours on an gpu-8g. Either prune to a greedy/beam-2, 1-layer-per-step sweep (~200–400 candidate evals) or seed the layer order from D1's per-layer ranking and evaluate one sweep. Also: an attention *mask* in HF saves zero bytes; the tok/s half needs a runtime that actually keeps a W-entry ring buffer for the windowed layers (per-layer SWA KV as used for Gemma-style models in llama.cpp, or a patched cache) — a code dependency, not just a measurement.
8. Source quirk, faithfully copied: the Table 4 pattern string `SFSSFFSSSFFFFSSFSFFFFFFSFSFSSFSSFSFSSFSSS` has 41 characters (21 S, 20 F) for a 40-layer model with a stated 1:1 ratio. Do not rebuild the pattern from the string; only the ratio and the search recipe are usable.
9. Minor: the digest lists "GLM-5 report Sec 2.1" for "3 MTP layers share parameters" and Table 2 accept lengths — correct; and the "score → ReLU → top-k" description comes from the Ascend kernel section, not from an architecture definition (the report does not define the indexer's equations).

**Unsupported numbers** (not in any fetched source): "~37% fewer KV bytes/token" (derived); "3-6 GPU hours"; "~12 search steps"; "~50 RULER-lite prompts"; "within ~1.3 pts" (contradicted by Table 6).

**Corrected idea** — keep `lm-searched-swa-pattern-zero-train`; same lever (Table 4: searched 1:1 SWA pattern, 4096 window, RULER@16K 88.92 vs 92.01 full vs 25.89 naive interleave, zero training), but: model = Qwen3-0.6B for both halves; window 2K at 8K context (same 1/4 window:context ratio as the source); search = greedy or beam-2, one layer per step, seeded by D1's per-layer ranking, ~20 RULER-lite prompts per candidate; expected KV-read fraction 0.625 (derived, to be measured as tg tok/s on the swarm box with a real per-layer ring-buffer KV, not a mask). First falsifier: on Qwen3-0.6B bf16 at 8K, if no searched half-SWA pattern stays within 5 RULER-lite points of full attention at 8K while the alternating pattern collapses, the lever does not exist at 0.6B.
