## Summary (measured lines)

1. Model: "2.8T parameter Mixture-of-Experts model with 104 billion activated parameters, native vision capabilities, and a 1-million-token context window" (abstract). Table 1: 93 layers, hidden 7,168, 896 routed experts, 16 active, 2 shared, latent MoE dim "3584 (0.5x)", attention "69 KDA + 24 MLA", activation SiTU-GLU, 1 MTP layer, vocab 160K, ViT 401M / 27 layers.
2. Sequence mixing is a 3:1 hybrid: "Each block contains 3 KDA layers followed by 1 Gated MLA layer" (§2.1); KDA "replaces the growing key-value cache of softmax attention with a fixed-size recurrent state S in R^{dk x dv}" (§5.1); MLA layers use NoPE, so "the model extrapolates directly to 1M-token contexts without any positional-encoding modification" (§3.4).
3. KDA's decay is lower-bounded: "g = gmin Sigmoid(e^A z) in (gmin, 0)", "gmin = -5 is fixed", so every retention factor "> e^-5 ~= 6.7e-3", cumulative log-decay over a 16-token tile "lies in (-80, 0)", reciprocal "smaller than e^80 and remains within the BF16 dynamic range" — which "allows both diagonal and off-diagonal tiles to use dense Tensor Core matrix multiplications, eliminating the position-pair diagonal path" (§2.1.1).
4. Depth mixing is Attention Residuals: each layer softmax-attends with a learned pseudo-query over the embedding and preceding layer outputs; Block AttnRes drops the overhead "from O(Ld) to O(Nd)", "N ~= 8 recovers most of the benefit", K3 uses "8 blocks with 12-layer size" (§2.2).
5. Width mixing is Stable LatentMoE: routed experts run in a latent space of width l, "896 routed experts with 16 active experts per token, corresponding to a sparsity of 56"; stabilized by RMSNorm before W_up, SiTU-GLU (beta1 = 4 gate, beta2 = 25 up, output bound |f(x)| <= beta1*beta2 = 100), and Quantile Balancing (bias set from the (1-k/n)-quantile of router margins, estimated from a histogram of "a few hundred bins per expert") (§2.3).
6. Headline efficiency claim: the bundle (architecture + data + training recipe) yields "an approximately 2.5x improvement in overall scaling efficiency over Kimi K2" on held-out OOD validation loss vs FLOPs (Fig. 7, §3.2) — the paper does NOT attribute the 2.5x to any single component. Scaling-law study "consistently favors cosine decay over Warmup Stable Decay (WSD)" once each schedule gets its own hyperparameter search.
7. Deployment: MoE expert weights in MXFP4 with MXFP8 activations, QAT "throughout the entire post-training stage, covering both SFT and RL"; the pre-trained MTP layer is fine-tuned into an EAGLE-3-style draft "unrolled for seven steps", trained with the LK loss "-log sum_x min(p(x), q(x))" (the negative log acceptance rate) rather than KL (§4.1.4). Decode-side KDA state rollback under speculative rejection is done by caching only projected inputs and replaying on-chip (§5.4.2). MoE decode at small batch is "memory-bound streaming of weight matrices", served with a token-centric WarpDecode-style kernel where "each warp is responsible for one output neuron".
8. Case study: K3 autonomously designed an inference chip for "a nano model following the same architecture ... under group-wise INT4 weight quantization (group size 128)" that "closes timing at 100 MHz and achieves an RTL-simulated decode throughput of over 8,700 tokens/s, integrating 1.46M standard cells, 0.277 MiB of SRAM" within "4 mm2" (§7). The repo (nano-kpu, Apache 2.0) ships "LUT init hex (sigmoid/alpha/expneg/rsqrt/recip)" ROMs and "a bit-exact Python fixed-point model"; correctness bar "per-row logits cosine >= 0.98 and pooled argmax >= 0.99".
9. Cost: "On Kimi Code Bench 2.0, Kimi K3 is 4.0 points behind Claude Fable 5 at 38% of its cost"; "BrowseComp ... best score (91.2%) at $2.03 per task — half the cost of GPT-5.6 Sol (90.4%)" (§6.4). Overall "trails the most powerful proprietary models, namely Claude Fable 5 and GPT-5.6 Sol" (abstract).

## Relevance to local-maxxing

Nothing here runs on the town's iron (2.8T total, 104B active; even the MXFP4 expert-only footprint is far past 23 GB), so K3 is a source of *mechanisms*, not weights. On the bytes-per-token ledger the mechanism that matters is the 3:1 KDA:MLA hybrid: 69 of 93 sequence-mixing layers read a fixed dk x dv state per head every token instead of a KV cache that grows with context, and the town's own decode is bandwidth-bound (Qwen3-0.6B Q8_0 at 34-45 tok/s ~= one process's copy bandwidth) — at long context the per-step KV read competes with the weight read, and a constant-state layer removes that term outright. Lower-bounded decay (alpha > e^-5, log-decay in (-80, 0) per 16-token tile) is a fixed-point-range argument in disguise and lands squarely on the E3 byte-neuron LUT / flip thread: a bounded leak on a leaky-integrator state is what makes an 8-bit cascade representable, and the nano-kpu repo is an open, bit-exact fixed-point reference (INT4 g128, LUT ROMs for sigmoid/alpha/expneg/rsqrt/recip) of exactly this hybrid, runnable in Verilator on local-town's 8 cores. Block Attention Residuals (softmax over <= 8 previous block outputs, O(Nd) extra bytes/token) is the obvious depth-side complement to the recurrent looped transformer, whose single residual stream over loop iterations is the same "RNN-over-depth" bottleneck the paper names. The MTP->EAGLE-3 draft with LK loss is the cheap reminder that on bandwidth-bound decode every accepted draft token divides bytes/token; and §6.4's cost-per-task table is the pricing input for powering the swarm's kids off OpenRouter in bursts.

## Idea seed

- slug: `lm-kda-constant-state-kv-bytes`
- title: Hybrid 3:1 linear-attention layers to cap per-token KV bytes on bandwidth-bound decode
- lever: Replace 3 of every 4 attention layers with a KDA-style fixed-size recurrent state (dk x dv per head, alpha lower-bounded at e^-5) so the per-decode-step KV-cache read stops growing with context — K3 runs 69 KDA + 24 MLA layers and the only per-token sequence-mixing bytes in the KDA layers are the state, not the history.
- buys: A kid-sized looped transformer trained on local-town whose decode bytes/token on the swarm box stay at (weights + constant state) at 8K-32K context instead of (weights + ctx x KV-per-token), which is the regime where the town's 0.6B-4B models currently lose tok/s to the cache; the same bounded-decay state is a candidate substrate for the flip-mode SNN (leaky 8-bit state, decay in log space).
- first_falsifier: On the swarm box, `llama-bench` Qwen3-0.6B Q8_0 tg at prompt depth 256 vs 8192 — if tg at depth 8192 is within 10% of tg at depth 256, KV bytes are not a material share of the town's decode budget and a constant-state layer buys nothing at the contexts the town actually runs. (Town arithmetic, not from the source: Qwen3-0.6B has 28 layers x 8 KV heads x 128 dim x 2 (K,V) x 2 B = ~112 KB/token of f16 KV, so ~0.9 GB read per step at 8192, comparable to the ~0.6 GB Q8_0 weight read — expect a large drop; if it does not appear, the ledger is wrong somewhere and that is itself the finding.)
- cheapest_test_on_our_iron: Swarm box (arm-cloud 4c), `llama-bench -m qwen3-0.6b-q8_0.gguf -p 0 -n 64 -d 256,2048,8192`, ~10 minutes wall-clock, $0; if the drop is real, the follow-up is a ~20M-param 4-layer looped block trained twice on local-town (gpu-8gS), plain vs 3:1 gated-delta + NoPE softmax, matched tokens, ~2-3 GPU-hours, $0, comparing val loss and measured decode bytes/token.

## Critique (adversarial, 2026-09-16)

Re-fetched independently: https://arxiv.org/abs/2607.24653 HTTP 200 106,718 B ("Submitted on 27 Jul 2026 (v1), last revised 7 Aug 2026 (this version, v2)"); https://arxiv.org/pdf/2607.24653 HTTP 200 1,790,685 B, 47 pages, `pdftotext -layout` 3,173 lines; https://raw.githubusercontent.com/MoonshotAI/nano-kpu/HEAD/README.md HTTP 200 5,481 B; plus https://huggingface.co/Qwen/Qwen3-0.6B/raw/main/config.json HTTP 200 to check the town arithmetic in the falsifier. Every number in the Numbers list and the idea seed was grepped against the PDF text and found (Table 1 at PDF-text lines 743-768; §2.1.1 lower-bounded decay lines 340-345; §2.2 lines 406-424; §2.3 lines 426-433, Fig. 4 caption; §3.2 line 708; §3.3-3.4 lines 777-805; §4.1.4 lines 929-961; §5.4.1 lines 1557-1597; §5.4.2 lines 1617-1630; §5.4.3 lines 1675-1687; §5.3.2 line 1509; §6.4 lines 2071-2098; Table 5 lines 2078-2092; Fig. 14 lines 2172-2178; §7 lines 2207-2229). Section numbers all match the PDF's own headers. **No fabricated or misquoted number found.** The defects are in attribution and in the reader's inferences:

1. **"N ~= 8 recovers most of the benefit" is cited, not measured.** The PDF (line 423) reads "Empirically, N ≈ 8 recovers most of the benefit across model scales [58]" — that is the AttnRes paper's result, not a K3 ablation. Correction: attribute to ref [58]; K3 only reports its own choice of "8 blocks with 12-layer size, giving a partial final block and 9 total blocks when counting the embedding layer".
2. **"softmax over <= 8 previous block outputs" (Relevance) undercounts.** Eq. 10 (line 415-417): a layer i >= 2 in block n attends over [b0, ..., b_{n-1}, b_n^{i-1}]; with 9 blocks counting the embedding, the last block's layers see up to 9 sources, and "the final output layer then aggregates all N block representations". Correction: the value set is at most N+1 entries (N block sums plus the running partial), overhead O(Nd) with N = 8 as stated.
3. **"a fixed-point-range argument in disguise" / "candidate 8-bit substrate for the flip-mode SNN" / "leaky 8-bit state, decay in log space" (Relevance, idea `buys`) is the reader's mechanism, not the source's.** The source's argument (lines 340-345) is that with g_min = -5 the reciprocal rescaling over a 16-token tile is "smaller than e^80 and remains within the BF16 dynamic range", so causal tiles can be dense Tensor Core matmuls. A range of 80 nats is a BF16 8-bit-*exponent* argument; nothing in the source bounds the state S itself, and an 8-bit fixed-point state is nowhere claimed or tested. Correction: drop the 8-bit-substrate clause from `buys`; the only thing the source supports is "lower-bounded log-decay keeps the chunkwise reciprocal in BF16 range".
4. **The lever's cost saving is asserted by the source, not demonstrated.** The source states KDA "replaces the growing key-value cache of softmax attention with a fixed-size recurrent state" that is "cheap to transfer and reuse" (line 1170-1172), but reports no decode tok/s, bytes/token, or latency-vs-context measurement for the hybrid. The one measured efficiency number, "approximately 2.5x" (line 708, Fig. 7), is *training* scaling efficiency (OOD validation loss vs FLOPs) for the whole bundle, and the digest correctly says it is unattributed. Correction: the lever survives as a mechanism the source deploys at 2.8T scale, but the decode-bytes saving is the town's own hypothesis and must be measured here — which is what the falsifier is for.
5. **The first falsifier conflates KV bytes with attention FLOPs.** Town arithmetic (verified against the HF config: 28 layers, 8 KV heads, head_dim 128 -> 28 x 8 x 128 x 2 x 2 B = 114,688 B/token, so ~0.94 GB of f16 KV at depth 8192) is right, but at depth 8192 the per-token attention arithmetic (28 layers x 16 heads x 8192 x 128 x 4 ~= 1.9 GFLOP) exceeds the ~1.2 GFLOP of weight matmuls for a 0.6B model, so on a 4-core CPU a tg drop at depth 8192 can be compute-bound rather than byte-bound, and a "large drop" would not by itself confirm the bytes-per-token story the lever depends on. Correction: run each depth twice, f16 KV and `-ctk q8_0 -ctv q8_0` (halves KV bytes at identical FLOPs); the byte attribution holds only if the tok/s gap between the two grows with depth in proportion to the KV bytes removed. If q8_0 KV does not move tg at depth 8192, the town's decode cost at that depth is attention compute, and a constant-state layer would be buying FLOPs, not bytes — a different lever with a different grade.
6. **The local-town follow-up inherits a BF16 assumption the gpu-8gdoes not meet.** The source's dense-tile trick holds "within the BF16 dynamic range" (line 344). Turing has no BF16 Tensor Core path; FP16's maximum (65,504 ~= e^11.1) cannot hold a reciprocal "smaller than e^80". Correction: the ~20M-param comparison must run the chunkwise KDA path in FP32 (or Kimi Linear's log-space-relative-decay tiles), which changes the GPU-hour estimate and means the K3-specific "eliminating the position-pair diagonal path" gain is not reproducible on that card; the recurrent (decode) form is unaffected.
7. **nano-kpu numbers are synthesis-stage estimates, and the repo disclaims official status.** README: "area and timing are measured at the synthesis stage — pre-layout estimates ... not validated through backend place & route", "not sign-off values"; "Disclaimer: This is a demonstration of Kimi K3, not an official project by Moonshot AI." The PDF's "closes timing at 100 MHz" / "4 mm2" are quoted correctly but should carry that weight. Also README: the MoE is "top-2 routed experts + one shared expert" and Block AttnRes uses "a block size of two" (PDF line 2223) — a much smaller configuration than K3's 16-of-896 / 12-layer blocks, so it is a reference for the *fixed-point KDA + NoPE-MLA + AttnRes dataflow*, not for K3's sparsity.
8. **Reader-estimated numbers not from any source** (labelled as such in the seed, listed here so nobody re-cites them as measured): ~112 KB/token, ~0.9 GB KV read at 8192, ~0.6 GB Q8_0 weights, ~10 min wall-clock, ~20M params, ~2-3 GPU-hours.

Verdict: digest kept; grounded 4/5 (numbers all trace; three reader mechanisms leaked into Summary/Relevance/idea as if the source's). Corrected idea below tightens the falsifier to separate bytes from FLOPs and drops the 8-bit-substrate clause.

- corrected slug: `lm-kda-constant-state-kv-bytes`
- corrected lever: 3:1 KDA:MLA hybrid (69 KDA + 24 MLA in K3) replaces the per-layer KV cache in 3 of 4 sequence-mixing layers with a fixed dk x dv state per head, so the per-decode-step sequence-mixing bytes in those layers stop growing with context — a mechanism the source deploys but does not measure for decode; the town measures it.
- corrected first falsifier: on the swarm box, `llama-bench` Qwen3-0.6B Q8_0 tg at depths 256/2048/8192 with f16 KV and with `-ctk q8_0 -ctv q8_0`; if tg at 8192 is within 10% of tg at 256, OR the f16-vs-q8_0 KV gap at 8192 is under 10% while tg still drops, KV *bytes* are not the town's decode cost at these depths and the lever buys nothing here.
