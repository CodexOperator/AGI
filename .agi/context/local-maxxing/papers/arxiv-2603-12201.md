## Summary (measured lines)

1. **Setting (p.1-3).** DeepSeek Sparse Attention (DSA) puts a "lightning indexer" at every layer that scores all L preceding tokens and keeps the top-k ("k =2048 ≪ L"), so core attention is O(Lk) but "the indexer itself still operates at O(L²) at every layer", total "O(NL²)". Profiled on a 30B DSA model, the indexer's share of latency is "27%" at 10K rising to "81%" (prefill) / "68%" (decode) at 200K context (Fig. p.2).
2. **Observation (p.2, App. A p.16).** Pairwise top-k overlap |T(i)∩T(j)|/k, "averaged over 768 samples of 200K length": "Adjacent layers exhibit overlap ratios of 0.7-1.0"; block clusters "layers 3-5, 6-8, 17-30, 31-36"; early-vs-late corners "overlap ≤ 0.4".
3. **Mechanism (Fig. 2 p.3, §3 p.4).** Layers get a pattern string c ∈ {F,S}^N: F layers run their indexer and write `Tcache`; S layers "simply skip the indexer forward pass and reuse the cached index tensor from its F predecessor". "The first layer is always F." The cache "requires no additional GPU memory beyond what standard DSA already allocates" — one conditional branch.
4. **Training-free variant = greedy loss search (Alg. 1 p.5).** Start all-F, for K steps flip the single F→S that minimizes LM loss on a fixed calibration batch (paper: "batch size of 768 and a context length of 200K", p.7); "N(N−1)/2 forward passes" for a full all-F→all-S search. The per-step loss curve separates "easy" layers ("the first 20 steps") from "critical" ones ("after 35 steps") on the 47-layer model. Two cheaper proxies FAIL (App. C p.17-18): uniform interleaving and a DP over a cosine-similarity matrix both degrade like the naive baseline (Table 5: Avg 54.0 → 50.7 uniform → 49.8 similarity-searched at 1/2), because "per-layer output similarity is a local metric" and missing "a small number of critical tokens" cascades.
5. **Training-aware variant (§3.2 p.6).** Retained indexer distilled with a multi-layer KL against every layer it serves; Prop. 1 proves the gradient equals distilling to the averaged target p̄. Trained as "a 1,000-step dense warm-up phase followed by a 4,000-step sparse training phase" at 200K context (p.7). With it, uniform interleave matches full: 1/2 uniform Long Avg 51.6 vs baseline 51.0; dropping the cross-layer loss → 49.8, AA-LCR 49.8 → 44.0 (Table 3 p.9).
6. **Results (Table 1 p.7, Table 2 p.8).** 30B DSA (GLM-4.7-Flash base, "30B-A3B MoE ... MLA and 47 layers"), SGLang, H100 node, dp=8. At 200K: prefill 19.5 s → 10.7 s (1/4 retained, "1.82×"); per-request decode 58.0 → 86.0 tok/s ("1.48×"); full-KV throughput 197 → 297 tok/s ("1.51×"). Quality at 1/4 with searched pattern: Long Avg 49.9 vs 50.2, G&R 74.9 vs 74.6; uniform 1/4 collapses to Long 43.0; 1/8 searched 46.1 ("non-negligible"). GLM-5 (744B, 40B active) training-free 1/4 searched: Long Avg 78.0 vs 78.4 (Table 4 p.10); "∼ 1.2× end-to-end speedup" at 1/2 (Fig. 1 caption p.1).
7. **Generality claim (p.11).** "the core principle extends to any sparse attention method that ... involves a dynamic token selection step: for instance, the block-level selection in MoBA and NSA". Prior anchor-layer methods (TidalDecode, Kascade, HySparse) "rely on full attention at anchor layers"; here the oracle is the cheap indexer.

## Relevance to local-maxxing

**On the bytes-per-token ledger this is a decode-side bandwidth save, not only a FLOP save.** At decode the DSA indexer for one new token scores every one of the L cached indexer keys at every layer — a full-context read per layer — which is why per-request decode is only 58 tok/s at 200K and rises to 86 when 75% of those reads are skipped (Table 1). The paper's lever therefore reads directly as "bytes touched per token ∝ (N_F·L + N_S·k)" instead of N·L for the selection step. The town has no DSA model, but the same identity applies to any dense small model given a top-k attention selector: an S layer that inherits indices reads k KV rows instead of L. For Qwen3-0.6B (28 layers) on the swarm box, where tg is already at copy bandwidth, that is the one place long-context decode can get cheaper without a smaller model.

**The methodological finding matters more than the speedup.** Two cheap proxies — uniform interleave and cosine-similarity DP — fail at 1/4 retention (Long 43.0 and Table 5), while a global LM-loss greedy search recovers 49.9/50.2. That is the same shape as D1 on Qwen2.5-0.5B: the global proxy anti-predicts, per-layer end-to-end loss predicts. IndexCache says it a second time, on a 30B model, for a different kind of "drop": the cheap-to-drop layers are found by measuring LM loss after the drop, never by measuring the layer's local similarity. D1's mean-ablation harness is already the right instrument; the search here is D1's greedy loop with "flip this layer's selector to shared" in place of "mean-ablate this layer".

**Looped transformer and flip/SNN.** In a depth-recurrent block, "cross-layer" becomes "cross-iteration": the top-k index computed on loop 1 can be cached and reused on loops 2..K exactly as an S layer reuses its F predecessor, and the pattern string c becomes a per-iteration recompute schedule found by the same greedy search. The index tensor itself is a slowly-changing binary mask (adjacent overlap 0.7-1.0), i.e. a set of bits where only the flips carry information — the natural E3/chain-2 representation is "recompute an index only on a flip event", which is IndexCache with an event-driven rather than fixed schedule. Whether flip-rate across layers correlates with the searched F positions (early layers, transition layers) is a measurable question on our iron.

**Cluster fit.** The paper's regime (200K context, H100 node, 30B/744B) is far off ours; the transferable object is the 47-character pattern and the search algorithm, both of which run on local-town's GPU2070S against a 0.6B model at 4-8K context in minutes per forward. Nothing here needs OpenRouter spend.

## Idea seed

- **slug:** `lm-cross-layer-topk-index-reuse`
- **title:** Compute the attention top-k once per block of layers, reuse it below; pick the blocks by LM-loss greedy search
- **lever:** Skipping the token-selection pass on 75% of layers cut per-request decode from 58.0 to 86.0 tok/s and prefill from 19.5 s to 10.7 s at 200K on a 30B DSA model (Table 1) with Long Avg 49.9 vs 50.2 (Table 2) — bytes/token for the selection+KV read drop from N·L rows to (N_F·L + N_S·k) rows, and the pattern is found by greedy LM-loss search, since similarity-based proxies fail (Table 5).
- **buys:** On the swarm box's bandwidth-bound decode of Qwen3-0.6B/4B, a top-k KV selector on ~1/4 of the layers with shared indices below lets long-context (4K-32K) decode read k KV rows per S layer instead of L, which is the only route to cheaper long-context tok/s that does not shrink the model; the same F/S schedule transfers to the looped transformer as "recompute the index on iteration 1, reuse on 2..K".
- **first_falsifier:** On Qwen3-0.6B at 8K context over 64 calibration sequences, the mean adjacent-layer top-k (k=256) attention-index overlap is below 0.5 (the paper's regime is 0.7-1.0) — then there is nothing to share and the idea dies before any search.
- **cheapest_test_on_our_iron:** local-town (GPU2070S, torch venv), Qwen3-0.6B in fp16 via transformers with eager attention: dump per-layer per-head top-256 attention indices for 64×8K tokens, compute the 28×28 overlap matrix, then run the greedy F→S search (28·27/2 = 378 forwards at 8K ≈ 1-2 h wall-clock, $0) and report PPL at 1/2 and 1/4 retention versus uniform interleave.

## Critique (adversarial, 2026-09-16)

Re-fetched independently, same methods, byte-identical to the Provenance table: abs 200 / 43,514; HTML 200 / 274,826 (figure on p.2 is not rendered in the HTML, so it could not be cross-checked there); PDF 200 / 533,208, 18 pages, `pdftotext -layout` 1,175 lines, read in full. Bar labels on p.2 were pinned with `pdftotext -bbox` (x-coordinates), Qwen3-0.6B facts from https://huggingface.co/Qwen/Qwen3-0.6B/raw/main/config.json (HTTP 200: `num_hidden_layers` 28, `num_attention_heads` 16, `num_key_value_heads` 8, `head_dim` 128, `hidden_size` 1024).

**Verdict: keep the digest; grounded 3/5.** Every table number (Tables 1-5, App. A/B/D, p.5, p.7) traces to the PDF. The errors are one misread figure, a byte-accounting formula the source contradicts, two mechanism claims that are the reader's rather than the paper's, and a cheapest-test that is not runnable as written.

### Errors and corrections

1. **Summary line 1 and the returned `numbers` field: "81% prefill / 68% decode at 200K" — wrong.** The p.2 figure has four columns; `pdftotext -bbox` puts `81%` and `41%` at x=487.8 (the 200K column, x=486.3) and `68%` and `38%` at x=438.9 (the 120K column, x=437.4). Decode share at 200K is **41%**, not 68%; 68% is the *prefill* share at 120K. The digest's own Numbers line ("120K → 68% / 38%; 200K → 81% / 41%") is correct and contradicts Summary line 1. Consequence: the decode-side indexer share tops out at 41%, which bounds the decode speedup (1.48× observed) far below the prefill one (1.82×) — the reader's "decode-side bandwidth lever" is the *weaker* of the two levers in the source, not the headline.

2. **Lever formula "bytes/token for selection+KV read fall from N·L rows to (N_F·L + N_S·k) rows" — contradicted by the source.** p.4: "a large fraction of the O(NL²) total indexer cost can be eliminated while the O(NLk) core attention remains unchanged." In DSA every layer, F or S, already reads only k=2048 KV rows for core attention; IndexCache changes nothing about KV reads. What an S layer skips is the *indexer* pass — scoring all L cached indexer keys ("few heads, low-rank projections, and FP8", p.3). The correct accounting is: indexer-key touches N·L → N_F·L; KV touches N·k → N·k (unchanged). The reader's formula mixes the two and attributes a KV-read saving the paper does not claim.

3. **"This is a bandwidth lever, not only FLOPs" — the reader's framing, not the source's.** The words "bandwidth", "bytes", "memory-bound" and "HBM" do not occur in the paper body (grep: the only hit is the title of the SparQ reference, p.13). The paper frames the indexer as O(L²) *compute* ("cheaper per-FLOP", p.3) and says only that "a per-token indexer pass over the full context ... becomes the bottleneck at long sequences" (p.8), without saying whether that bottleneck is bandwidth or FLOPs. The bytes reading is a plausible reader inference (at 200K, N·L = 47×200K indexer rows per token vs N·k = 47×2048 KV rows) but must be labelled as such; the digest presents it as the paper's lever.

4. **"Buys": "an S layer that inherits indices reads k KV rows instead of L" on a dense model — that is the prior-work mechanism the paper explicitly distinguishes itself from, not IndexCache.** §2.2 (p.4) and §5.2 (p.11): TidalDecode, LessIsMore, OmniKV, DELTA, Kascade and HySparse "reuse top-k indices from periodic anchor layers for sparse decoding" and "all of these methods rely on full attention at anchor layers." IndexCache's stated novelty is that "the oracle is fundamentally cheaper because we share the output of DSA's lightweight indexer" (p.11). Qwen3-0.6B/4B have no indexer, so on the town's models an F layer must be a *full-attention* anchor (reads all L keys) — i.e. the idea on our iron is TidalDecode/Kascade, with IndexCache contributing only (a) the greedy LM-loss search in place of Kascade's DP over a similarity matrix and (b) the negative result that similarity-DP does no better than uniform on DSA (Table 5). Keep the idea; fix its provenance. Note also that Kascade "identifies head-aware remapping as critical" (p.11) — the DSA indexer is per-token (head-aggregated, p.4 "averaging softmax attention weights across heads"), whereas a dense GQA model's top-k is per head; the analog must choose head-averaged or per-KV-head indices and say which.

5. **"local proxies ... anti-predict" — overstated.** The source says the similarity-DP pattern "perform[s] comparably to uniform interleaving" and offers "no meaningful advantage" (App. C, p.18; Table 5: 49.8 vs 50.7, on a 3-benchmark Avg, not Table 2's 5-benchmark Long Avg). "Lack the discriminative power" (p.17) is not "anti-predict". App. A (p.16-17) also says **top-k index overlap itself is one of the local metrics that fails to identify the pattern** — relevant because the reader's first falsifier is an overlap gate. Overlap is a valid *necessary-condition* gate (no overlap → nothing to share) but the paper says it does not tell you *which* layers to share.

6. **Cheapest test is not runnable as written on local-town (8 GB).** (a) HF eager attention at 8K materializes a 16×8192×8192 score tensor per layer — 2.1 GB in fp16 plus the fp32 softmax upcast (4.3 GB) — on top of ~1.2 GB of weights and the KV cache; that OOMs a GPU2070S. (b) "378 forwards" mislabels the unit: Alg. 1 / p.5 counts N(N−1)/2 **loss evaluations over the whole calibration batch D**, so 378 × 64 sequences = 24,192 sequence-forwards of 8K tokens; at roughly 25 TFLOP per 8K forward for a 0.6B/28-layer model this is on the order of a day on a GPU2070S, not "1-2 h" (estimate, not measured; the "1-2 h" is likewise unmeasured and unsupported by any source). (c) Stopping at 1/4 retention needs only K=21 steps, i.e. 27+26+…+7 = 357 evaluations, not 378 — a small saving, but the paper's block-parallel trick (p.5) does not apply on one GPU. Corrected test below.

7. **"the only route to cheaper long-context tok/s that does not shrink the model" — overclaim, not in source.** KV quantization, KV eviction, sliding-window/hybrid layers (which the paper itself lists, §5.1 p.10) are other routes. Say "one route".

8. **Minor.** The Summary's "Table 5 similarity 49.8 vs uniform 50.7" sits beside Table 2 numbers without noting that Table 5's `Avg` is over MRCR v2 / GraphWalks / RULER only (3 benchmarks, original 54.0) while Table 2's `Long` is over 5 (original 50.2); the two averages are not comparable. The looped-transformer transfer ("cross-layer → cross-iteration") and the E3/chain-2 "recompute on a flip" reading appear nowhere in the paper and are correctly labelled as the reader's in the Relevance section — but they migrate unlabelled into the idea's `buys`.

### Corrected idea seed

- **slug:** `lm-cross-layer-topk-index-reuse`
- **title:** Share top-k attention indices across layer blocks; pick the blocks by greedy LM-loss search, not similarity
- **lever:** IndexCache skips the per-layer top-k *selection* pass on 75% of layers (index reuse from the nearest F layer, one conditional branch, Fig. 2) and on a 30B DSA model at 200K that cut prefill 19.5 s → 10.7 s (1.82×) and per-request decode 58.0 → 86.0 tok/s (1.48×) at Long Avg 49.9 vs 50.2 (Tables 1-2); the indexer's cost goes from N·L to N_F·L per token while KV reads (N·k) are unchanged (p.4), and the pattern must come from a greedy LM-loss search because uniform interleave and similarity-DP both fall to 43.0 / ~uniform (Tables 2, 5).
- **buys:** On the town's dense Qwen3 models there is no indexer, so the town-side version is the anchor-layer scheme the paper cites as prior work (TidalDecode/Kascade: F layers do full attention, S layers gather only k KV rows) with IndexCache's search replacing Kascade's similarity DP; if adjacent-layer overlap holds on Qwen3-0.6B, an S layer's KV traffic at 4K-32K context drops from L to k rows per KV head — one route (not the only one) to cheaper long-context decode without a smaller model, contingent on a sparse-gather attention kernel that llama.cpp does not have today. Cross-iteration reuse in a looped transformer is the reader's untested extension.
- **first_falsifier:** On Qwen3-0.6B at 4K context over 16 calibration sequences, head-averaged (per the paper's p_t definition, p.4) top-256 index overlap between adjacent layers averaging below 0.5 (paper's DSA regime: 0.7-1.0, App. A) kills the idea before any search; overlap above 0.5 does not confirm it (App. A/C: overlap is a local metric that does not pick the pattern).
- **cheapest_test_on_our_iron:** local-town (GPU2070S 8 GB, torch venv), Qwen3-0.6B bf16 with SDPA plus a hooked, chunked q·kᵀ per layer that computes a head-averaged top-256 mask and can substitute a cached mask from the nearest F layer: (1) 28 forwards over 16×4K to build the 28×28 overlap matrix (minutes); (2) greedy F→S to K=21 (357 batch loss evaluations × 16 sequences of 4K, budget ~2-4 h at a rough ~1 s per 4K forward — measure one forward first and rescale), $0; report PPL for searched vs uniform at 1/2 and 1/4 retention. No swarm-box tok/s claim is possible from this run; that needs a gather kernel.
