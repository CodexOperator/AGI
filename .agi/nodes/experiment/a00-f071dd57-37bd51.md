# experiment:a00-f071dd57-37bd51

## Experiment

Read-only source + live measurement against the hypothesis "the kill watchdog keys on MemFree (os.freemem), not MemAvailable". Found the exact kill source in the runtime binary, identified which memory signal it reads, and took a live snapshot of the MemFree/vs/MemAvailable divergence on this box.

### (1) KILL SOURCE — the Claude Code CLI's own background-task supervisor, not the agi/pi harness

The literal message "stopped because the system is running low on memory" lives in the `ccd` Claude CLI binary at `/home/ubuntu/.local/share/claude/versions/2.1.267` (VERSION 2.1.267, built 2026-09-09, embedded Bun v1.4.1). Its low-memory gate is a function (deobfuscated name `$on`) keyed on the feature flag `tengu_bg_low_mem_mb`:

```js
import{freemem as N}from"os";
function $on(){
  let e=P("tengu_bg_low_mem_mb",1024)*1024*1024;   // default 1024 MiB
  if(e<=0)return{lowMem:!1,level:void 0};
  if(M()!=="macos")return{lowMem:N()<e,level:void 0};  // LINUX: os.freemem() < 1GiB
  let n=K();return{lowMem:n!==void 0&&n>=I,level:n};    // macOS: memoryPressureLevel critical
}
```

Signal sent: not the kernel OOM killer and not shell job-control. It is the **CLI daemon's own supervisor** reaping *settled* (idle/blocked) background workers to shed memory. On lowMem two things happen: (a) the periodic sweep shortens the idle-retire window for settled workers from 1h to 60s (`ce=le?Je:ir`, `Je=60000`, `ir=3600000`); (b) before spawning a new background task while lowMem it retires already-settled workers first (`for(let ae of a.values())ae.retireIfSettled(Je,H)..."low memory"`). A retired worker is written as `state:"stopped", status killed` with the "stopped because the system is running low on memory" detail. This confirms the brief's standing mechanism claim: `nohup`/backgrounding does NOT shield a process, because it is the harness/CLI supervisor stopping the task, not anything at the process level.

### (2) THE DECISIVE FINDING — os.freemem() reads MemAvailable in this runtime, NOT MemFree

The hypothesis's mechanical premise is that `os.freemem()` = MemFree (excludes reclaimable page cache). In the runtime actually embedded (Bun v1.4.1) that is **false**: Bun fixed `os.freemem()` on Linux to read **MemAvailable** (`/proc/meminfo` `MemAvailable:`), matching Node.js, in PR oven-sh/bun#29080 landed **2026-04-09** — five months before Bun v1.4.0 (2026-08-20) / v1.4.1 (2026-09-04). The same change is libuv/libuv#3351. Live cross-check on this box (system Node 22):

```
node -e "...os.freemem()"  ->  17558 MB  == MemAvailable (18090296 kB ≈ 17.2 GiB)
                                   NOT MemFree (1141908 kB ≈ 1.09 GiB)
```

So the gate is effectively `MemAvailable < 1024 MiB`. That is the exact "falsifiable" branch the hypothesis carves out: the watchdog reads MemAvailable, therefore the hypothesis is false.

### (3) LIVE DIVERGENCE SNAPSHOT — the divergence is real but points the wrong way

```
free -h:      total 23Gi  used 6.2Gi  free 1.1Gi  buff/cache 16Gi  available 17Gi
/proc/meminfo: MemTotal 24550508 kB | MemFree 1141908 kB | MemAvailable 18090296 kB
              Buffers 3009596 kB | Cached 12244356 kB | Swap 4Gi (946Mi used)
```

The MemFree-vs-MemAvailable divergence the hypothesis predicted EXISTS on this machine (MemFree pinned at ~1.1 GiB by a 16 GiB page cache while MemAvailable is 17.2 GiB) — but the watchdog reads the **high** number (MemAvailable), not the low one, so under current load it sits nowhere near its 1 GiB threshold and the predicted *spurious kill* does NOT follow. The phenomenon is the mirror image of the hypothesis.

Reasons, plainly: this kid context is not the interactive CLI daemon that owns background workers (the supervisor that performs the retire), and the gate signal (MemAvailable) is ~17 GiB, seventeen times above the 1024 MiB threshold. Inflating page cache would narrow MemFree but the gate does not look there. A live reproduction would require running inside the CLI daemon while MemAvailable is driven under 1 GiB — not achievable read-only in one turn. Per the brief, this non-reproduction is reported as weaker evidence, not as a settled reproduction.

### VERDICT

Hypothesis l4-oom-watchdog-signal, as worded ("keys on MemFree / os.freemem") is **disproved as the mechanism**: the runtime's `os.freemem()` reads MemAvailable (Bun #29080, embedded v1.4.1), so the gate is MemAvailable < 1024 MiB — precisely the falsifiable alternative the hypothesis names as making it false. Confidence 0.75; held to a lean (not full disproved) because the same-binary `os.freemem()` value is inferred from the documented fix + version timing + matching Node behaviour rather than executed directly on the embedded binary, and no kill was reproduced. The real-world question (what stopped that trivial task) therefore needs a different explanation than MemFree-vs-MemAvailable — see the remedy note.

### REMEDY (item 4)

- The only knob: the internal feature flag **`tengu_bg_low_mem_mb`** (default **1024** = 1024 MiB of MemAvailable), which the source reads directly. Setting it to 0 disables the low-memory gate. I did not verify a public/user-facing env var name for it; it is an internal tengu knob.
- Standing rule, with the mechanism named: long-running work goes in the **foreground with a long timeout (400000ms)**, not backgrounded. `nohup`/backgrounding provides NO protection here because the stop is the CLI's own supervisor retiring the settled background worker on its lowMem sweep — not the kernel OOM killer, not shell job control — so nothing at the process level can shield it.
