## Experiment

Measured the actual `grok-bot-cli` package rather than renaming the stub flags.
The configured host path is absent on this box and `grok-bot` is not on PATH,
so I used the already-installed authoritative npm package captured by a prior
scratch run: `grok-bot-cli@0.3.1` (package bin `grok-bot -> src/cli.js`) and ran
its executable read-only. Its help defines `send <bot-or-group> <message...>`
but neither `--model` nor any prompt-file/standalone `-p` flag. The complete
stdout is pinned at `extensions/agi/tests/fixtures/grok_bot_help.txt`.

Before the fix, the landed adapter emitted:

```text
['grok-bot', '--model', 'grok-4-fast', '-p', '/tmp/context.md']
```

That was a management CLI being treated as a model runner. I changed the one
`build_command` path to the measured send shape:

```text
['grok-bot', 'send', 'Researcher', 'work on the target']
```

The context file is read as the message. The required bot/group target is an
explicit `harness["target"]`; absent it, the adapter refuses by name rather
than guessing from an engine seat id. `model_args` is now empty because the
measured CLI has no model selector. Restart still calls this same builder, so
there is no second argv path. No dispatch/rotate special case was added.
