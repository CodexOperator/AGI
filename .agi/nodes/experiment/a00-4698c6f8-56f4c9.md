# experiment:a00-4698c6f8-56f4c9

## Experiment

**Question (the parent hypothesis's CLAIM, four conjuncts).** On the served `Qwen3.5-9B-Q4_K_M` with
`-fa on`, does the off-the-shelf K/V split `-ctk q8_0 -ctv q4_0`

1. cost <= 0.1 pct of the f16 NLL,
2. fit >= 1.8x the f16 slot (49,664 tokens) under the router's own `--fit`,
3. run its attention on the **GPU** in this build (its `FA_QUANTS` line lists only matched pairs), and
4. does the L1 stack -- the winner of {split, q4_0/q4_0} at `--fit-target 512` -- fit >= 3x?

**T0 guard (2026-09-23T14:32:13Z).** `spawn_budget.py status` 7/30 live, no pi-local round;
`GET :8080/slots?model=Qwen3.5-9B-Q4_K_M` -> `n_ctx 49664, is_processing false`;
host `MemAvailable` 5713 MB >= 2 GB; the only GPU compute app was the router
(`/app/llama-server, 6726 MiB`), so `docker stop llama-server` freed the card (`nvidia-smi
--query-compute-apps` empty after). RAM sampled through the round: 5671-12053 MB, never near 2 GB.

**Inputs.** Served model `/data/ml/models/Qwen3.5-9B-Q4_K_M.gguf` and the OSC.02 scratch copy
`/data/ml/scratch/osc02/Qwen3.5-9B-Q4_K_M.gguf`, both sha256
`03b74727a860a56338e042c4420bb3f04b2fec5734175f4cb9fa853daf52b7e8` (verified FIRST). Nothing was
written to any model file. Image `ghcr.io/ggml-org/llama.cpp:full-cuda` (llama.cpp 0.4.1-dev, build
11058 -- the same build as OSC.05/OSC.06).

**Method** -- one driver, `.agi/context/local-maxxing/kv/kv_split_round.py` (new; reuses
`kv_speed_round.parse/ram` by import, and OSC.05's args and read-points rather than rewriting them):

- **T1 placement** -- `llama-server` with the recorded router args (`--fit on --parallel 1
  --cache-reuse 8 --jinja`) + `-fa on -ctk q8_0 -ctv q4_0`, at `-lv 5` so the whole load log is
  readable; grep for the flash-attn / fallback / KV-buffer lines.
- **T2 quality** -- `llama-perplexity -m <gguf> -f wiki.test.raw -c 512 --chunks 40 -ngl 99 -fa on
  -ctk T -ctv T --seed 42 -t 8 --no-warmup`, f16 fresh today and the split.
- **T3 capacity** -- the same router args with `--fit on` (spare port, one slot) for the split ->
  `n_ctx_slot`; then q4_0/q4_0 with `--fit-target 512` -> `n_ctx_slot`.
- **T4 speed** (recorded, not a verdict input) -- `llama-bench -ngl 99 -fa 1 -ctk T -ctv T -p 512
  -n 64 -d 0,16384 -r 5`, one discarded warm-up, split vs q4_0/q4_0, same process conditions.

**Deviation, recorded (a real one).** The first split fit (`--fit on`) reported **86,528** tokens =
1.742x -- under the 1.8x bar. It was measured while a concurrent manual `llama-server` attempt of
mine (the T1 hand-check, which OOM-failed at 14:34) still held a stale CUDA context: 86,528 vs
92,416 is exactly 5,888 tokens x 13,312 B/token = **78 MB** of free VRAM, i.e. one CUDA context.
Three clean repeats after the round gave **92,416** (identical three times) with the f16 control
reproducing the router's own 49,664 twice. The contaminated figure is kept in the raw artifact and
the clean one is the verdict input; both are in the evidence file.

## Results -- T1 placement (the GPU question)

The build's own capability line, from `place_split.log` (identical for f16):

```
system_info: ... CUDA : ARCHS = 500,610,700,750,800,860,890,900,1200 | USE_GRAPHS = 1 |
  FA_QUANTS = q4_0-q4_0,q8_0-q8_0,f16-f16,bf16-bf16 | CPU : ...
```

No mixed pair is listed -- and yet, with the split:

```
llama_context: flash_attn            = enabled          (x3: text model, then the draft/ctx re-init)
llama_kv_cache:      CUDA0 KV buffer size =  1173.25 MiB
llm_load_tensors: layer 0..N assigned to device CUDA0
```

and the **KV cache itself lives in VRAM on CUDA0** (f16 control: `CUDA0 KV buffer size = 1552.00 MiB`
= 49,664 x 32,768 B exactly; the split's 1173.25 MiB = 92,416 x 13,312 B exactly). A grep of the
whole 3,862-line load log for `not supported|fallback|disabl` returns only the unrelated
`cache_reuse is not supported`, `preserve_reasoning kwarg`, and prompt-cache lines -- no attention
fallback. `-fa 0` with the split refuses to build a context at all
(`llama_bench: error: failed to create context`), which is llama.cpp's hard `V cache quantization
requires flash_attn` gate: FA is not merely decorative here.

**Speed cross-check.** If the attention op had been scheduled to the CPU backend, the scheduler
would copy the whole VRAM-resident K/V out over PCIe every token (d=16384: ~8 GB/token across 40
layers) -- three orders of magnitude below what was measured: the split decodes **48.76 +/- 0.79
tok/s at d 16384 (3 reps)**, 85 pct of f16's 57.14 tok/s (OSC.06, same box/image/build), and f16
*without* FA is 34.01 tok/s. CPU attention cannot beat GPU non-FA attention.

**Conclusion:** the split's attention runs on the GPU in this configuration, although the declared
`FA_QUANTS` list does not advertise the mixed pair. Recorded as inference from the KV-buffer device,
the enabled flag, the absence of a fallback message, and the speed -- not from a kernel-level trace
(`GGML_SCHED_DEBUG=2` produced no assignment lines in this build; the two `sched_*.log` files are
there as the negative record).

## Results -- T3 capacity

| config | fitted n_ctx | ratio to 49,664 | bar |
|---|---|---|---|
| split, `--fit on` (contaminated 1st run) | 86,528 | 1.742x | 1.8x |
| **split, `--fit on` (3 clean reps)** | **92,416** | **1.8608x** | **1.8x -- PASS** |
| f16 control, clean reps | 49,664 x2 | 1.0000x | -- (calibration: matches the router's own slot) |
| **L1 stack: q4_0/q4_0, `--fit-target 512`** | **156,416** | **3.1495x** | **3x -- PASS** |

The L1 stack reproduces OSC.05's margin-scan figure (156,416) exactly, which was the reproducibility
residue OSC.05 carried to this round. The split's byte model checks out: 13,312 B/token (K q8_0
8,704 + V q4_0 4,608) x 92,416 = 1,173 MiB, the KV buffer the log reports. Split at the router's
default margin buys **+86.1 pct context**; stacked with `--fit-target 512` q4_0/q4_0 buys 3.15x.

**Honest margin note.** The split clears 1.8x by 3.0 pct (92,416 vs 89,395), and `--fit on` is
margin/free-VRAM bound -- the 78 MB of stale context alone moved it from 1.861x to 1.742x. The pass
is real and reproducible at the router's default margin, but it is the thinnest of the four bars.

**The split IS an L1 sibling** -- with one qualification the round names plainly: q4_0/q4_0 stays the
**capacity** winner at the same margin (118,784 = 2.392x vs the split's 92,416 = 1.861x). What the
split buys is **quality headroom**: +86 pct context for +0.0162 pct NLL (vs q4_0/q4_0's +0.0741 pct),
at equal decode speed. That is the rung the Prime can use where NLL headroom matters more than the
last 30 pct of context.

**L1's largest safe step (the round's product).** q4_0 K+V with `--fit-target 512`:
**156,416 tokens = 3.15x today's 49,664 slot, at +0.0741 pct NLL, decode 46.7-51.4 tok/s at d 16384.**
If a lower NLL delta is wanted, the split at the router's default margin is the safer rung:
92,416 tokens = 1.86x at +0.0162 pct. The two are alternatives, not a stack.

**No router flag change is proposed by this round** -- the router, its `run.sh` and every box cell
were left untouched; the choice is the Prime's.
