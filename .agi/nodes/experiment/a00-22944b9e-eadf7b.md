**The index.lock fight (the real finding).** The lock was already present when I started:

| t (age) | action | result |
|---|---|---|
| 766s | `write.py ... set title` | rc 3, 19 commit tries, `fatal: ... index.lock: File exists` |
| 766s < 900s | inspect only | NOT stale by the tool's own rule — did not touch it |
| 968s | retry `write.py ... set title` | rc 0, `unchanged` — the first write HAD landed on disk |

The mechanism bug worth naming: **`write.py` writes the node to disk, then fails to commit, and
exits 3 — so a kid that reacts by retrying the same write is told "unchanged", which is TRUE and
misleading.** The work is on disk and uncommitted; the second call reports nothing changed
because the second call is a no-op. The recovery hint it prints (`git add`/`git commit` on the
one file) is a git command a kid is forbidden to run, so the only sanctioned path is to wait and
let `cli.py done` commit. That is what I did. Nobody should have to read a lock age to know a
write is already on disk.
