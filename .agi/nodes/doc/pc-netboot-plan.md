## BOOT
- The lab boots by PXE from encryption-town: pxe-dnsmasq (dnsmasq with enable-tftp) serves the kernel + initrd by TFTP, and its own log records EVERY TFTP file sent, with the client; nbd-server exports /data/nbd/localtown-root.img (11-05) as root. READ by belam 15:4xZ 11-18: that log already shows the 11-17 04:27Z restart PXE-booted.
- The image is brought to the crew's state on encryption-town while the container crew runs (no PC reboot): the NVIDIA driver for the image's kernel; the PC's CURRENT tunnel key and address config (the 11-05 image carries an older one, alive A1); the crew's units projected by agi.sh host at the CURRENT trunk pin, never 11-05's; the SSD dir (STORAGE) mounted as /fast; the watchdog CARRIED (UNLOCK (c) gates 1-3; measured in B5). Each read back from the image before PHASE B.
- (b) THE LEVER IS BOOT-FISH'S MODE, NOT THE FIRMWARE ('rig mode <name>' sets it, 'rig status' reads it; v4, belam's A1 read 15:2xZ 11-18): the firmware boots PXE FIRST, and Bazzite is reached only through boot-fish's 'bazzite' mode on encryption-town (its GRUB exit to the local entry 0006). So EVERY reboot of the PC, an accidental one included, already goes through boot-fish, and the mode decides the OS. Today's safety is the mode reading 'bazzite'; PHASE A never changes it (A0 and A4 read it). A PXE that fails outright (encryption-town or the tunnel unreachable) falls to the firmware's NEXT entry: PHASE B runs only if belam's A1 read names that entry as the local Bazzite one; any other entry = PHASE B BANKED.
- (a) THE WAY BACK, RUN REMOTELY AND SHOWN BEFORE THE STEP: mode 'bazzite' on boot-fish, READ BACK with host and time, then a reboot of the PC ('rig boot gaming', which sets mode 'bazzite' AND reboots: 'systemctl reboot' over ssh, or wake-on-LAN if the PC is off); the PC is read back up on Bazzite with the container crew running, BEFORE the first netboot. This is PHASE B's FIRST step, B0, on the owner's own ask (it is a reboot, so never in PHASE A). From the netbooted lab the same pair returns it: mode 'bazzite', then a reboot (or the watchdog's reset).
- Switching: one OS at a time on bare metal. Bazzite stays on the NV3 tonight; moving it off needs a new disk, not tonight's scope.

## UNLOCK
- (c) EVERY BOOT WITH NO ONE THERE: the lab image's root is unlocked BY HAND, remotely (rig unlock), which works only once the initrd has the network and its tunnel up; if it does not get there, the initrd waits at a prompt. READ in A1 (belam 15:2xZ 11-18): the 11-05 image's initrd arms NO watchdog, and there is NO remote power or reset path (no BMC, no smart plug). So a netboot that stops at the prompt or hangs is DOWN until the owner's hand. v6 RULE, three gates, each READ BACK in A3 (a config read is a carry, not a measurement), else PHASE B BANKED: (1) THE WATCHDOG IN THE INITRD: the built initrd CARRIES sp5100_tco (its module list) and systemd's RuntimeWatchdogSec (its config). (2) THE WATCHDOG AFTER SWITCH-ROOT: after switch-root PID 1 reads the ROOT image's system.conf, so the root image carries RuntimeWatchdogSec too, read back; and the plan names nowayout (whether a close of the device disarms it), read back. (3) THE UNLOCK DEADLINE HAS ITS OWN MECHANISM (alive 15:44:11Z): a passphrase prompt is not a hang, since PID 1 keeps pinging and the watchdog never fires; so the initrd carries a unit that forces a reboot at T+10 min unless switch-root is reached (e.g. a job timeout with a reboot-force action on the unlock), named and read back from the built initrd, plus panic=N on the lab's kernel cmdline, read back. The forced reboot then PXE-boots, boot-fish reads 'bazzite' (B2's one-shot), and Bazzite comes up.

## RISKS
- A1 REACHABLE IS READ, NOT ASSUMED: every remote way back runs from encryption-town over the tunnel that lost its address 11-14 (cause still unknown, goal:g7.16.1.11.47). B4's positive read = a FRESH tunnel handshake for the PC seen from encryption-town plus one ssh command answered, within 15 min of the reboot; its absence triggers the way back. NOT READ: whether ANY remote power or reset path exists (a smart plug, a BMC; a consumer board has no BMC). If none, a netboot that hangs before the watchdog is armed, or a PC that never reaches the network, leaves the lab DOWN until the owner is home; this cost is named here before any reboot, for the council and the owner to weigh.
- S3 A HANG IS NOT A FAILED BOOT: neither the boot order nor boot-fish's mode resets a box that booted and then hung. READ: the chipset watchdog exists (SP5100 TCO, 60 s) and the 11-05 initrd does NOT arm it. Carried by the initrd AND the root image (A3, read back; UNLOCK (c) gates 1-2) and measured active on the running lab (B5), it turns a hang into a reset -> PXE -> mode 'bazzite' -> Bazzite; a passphrase prompt is not a hang, so gate 3's forced reboot covers that case. Without it, there is no remote reset at all (A1: no BMC, no smart plug). 'rig wake' (if wake-on-LAN) starts a box that is off, never a hung one.
- A2 THE WAY BACK BOOTS THE FAILING DRIVE: Bazzite and the container sit on the NV3 (belam's 11-10 read: ~1.04 M media/integrity errors, rising, spare 100%). SMART is read again in PHASE A; a failing-now read means the way back may not exist, so PHASE B waits for that read and the owner's word.
- Root over the network: NOT READ whether the NBD root rides the LAN or the tunnel. Over the tunnel, a link loss freezes the OS outright (worse than today's stuck NFS); the watchdog then resets to Bazzite.
- Rollback per step: A2 copy fails -> nothing changed. A3 image work fails -> nothing on the PC changed. A4 a boot_id changed with no owner restart cited, or the mode moved off 'bazzite' -> STOP and report; nothing further. B0 the way back fails -> STOP: the rest of PHASE B is BANKED (the way back is not proven). B2 the mode does not read back, or does not return to 'bazzite' -> STOP before B3. B3/B4 fail -> mode 'bazzite' (already, by B2's one-shot), then the watchdog's reset, else the owner's hand (the named cost, which the A3 watchdog rule exists to remove). B5 red -> the way back; container crew restarted only after the image crew is down.
