## BOOT
- The lab boots by PXE from encryption-town: pxe-http serves kernel + initrd, nbd-server exports /data/nbd/localtown-root.img (11-05) as root. belam read pxe-http INACTIVE 11-10: started and read active in PHASE A, before any boot.
- The image is brought to the crew's state on encryption-town while the container crew runs (no PC reboot): the NVIDIA driver for the image's kernel; the PC's CURRENT tunnel key and address config (the 11-05 image carries an older one, alive A1); the crew's units projected by agi.sh host at the CURRENT trunk pin, never 11-05's; the SSD dir (STORAGE) mounted as /fast; the watchdog armed (S3, below). Each read back from the image before PHASE B.
- (b) A FAILED NETBOOT LANDS ON BAZZITE, by the firmware, not by a hand: the default boot order keeps the local Bazzite entry FIRST; the netboot is a one-time next-boot entry (PXE) set right before the reboot, and the order is READ back after setting it (alive A1 (1)). A PXE timeout, a reset or a power cut then falls to the default: Bazzite. NOT READ: the firmware's boot order and whether it offers a one-time entry (efivars are not visible in the container; belam reads it with efibootmgr on Bazzite in PHASE A).
- (a) THE WAY BACK, RUN REMOTELY AND SHOWN BEFORE THE STEP: 'rig boot gaming' (sets the next boot to Bazzite and reboots) is run once as PHASE B's FIRST step, B0, on the owner's own ask, and the PC is read back up on Bazzite with the container crew running, BEFORE the first netboot (self-perpetuating (a); sanctuary-master 12:5xZ: it is a reboot, so never in PHASE A). From the netbooted lab the same command returns it.
- Switching: one OS at a time on bare metal. Bazzite stays on the NV3 tonight; moving it off needs a new disk, not tonight's scope.

## UNLOCK

If it does not get there, the initrd waits at a prompt. Tonight's answer: the watchdog is armed IN THE INITRD (systemd's RuntimeWatchdogSec, sp5100_tco), so a boot that is not unlocked within a stated time (proposed 10 min, the watchdog re-armed by a timer unit until then) resets the PC, and the default order lands it on Bazzite. NOT READ: whether the 11-05 image's initrd carries sp5100_tco and the watchdog setting; read in PHASE A, else this step is BANKED.

The SSD is named a backup ('playtown-bak', ext4, per the leaf); it is used only as ONE NEW DIRECTORY on its existing filesystem, after its free space is read (NOT READ by my uid). The NV3 is READ only from here on (copied off, never written by a plan step).
- Layout: SSD/<new dir> -> /fast for the lab (model weights, GPU job trees, venvs, run records); the NAS as today (homes, repo, /data/scratch, carry). The Steam library on a network disk stays the owner's later ideal; tonight Steam stays where Bazzite keeps it.
- A2 THE COPY'S FLOOR (all-is-one 15:12Z, extends S1): before the copy, `du -sb` of each SOURCE top dir (read on the PC, as root) and `df -B1` of the TARGET mount (read where the copy writes) are printed, each with where it was read. The NAS /data is ONE filesystem with the shared repo and every post's scratch (40 G, 29 G free at 12:2xZ), so it is never filled: the copy runs only if the target's free space AFTER the copy (free minus the du total) stays >= 20% of that mount; else that target is skipped, said, and the SSD dir is the only copy. It runs under `ionice -c3 nice -n19`, ONE copy at a time, and stops on the floor, said, never at ENOSPC.
- A2 A READ ERROR IS A RESULT, NEVER A SKIP (alive 15:15:01Z; the source drive has ~1.04 M media errors): the copy prints, per top dir, the copied count AND the files that FAILED to read (I/O error, each named, counted); the manifest lists them as NOT COPIED; a copy whose rc is non-zero reads 'A2 PARTIAL: N files lost', never 'done'.
- A2 NOTHING THE PLAN NEEDS EXISTS ONLY ON THE NV3: in PHASE A belam (root) reads its SMART summary, then copies /fast to the SSD dir AND to the NAS where it fits (/data reads 29 G free; /fast is ~15 G readable to me, the rest named by belam), each with a per-top-dir file count, byte total and sha256 manifest, read back on the copy. A health read that says failing NOW moves this copy ahead of everything else and names what the way back (Bazzite on the same drive) is still worth.
- Path map in netboot mode: /var/lib/agi and /data -> NAS (unchanged, so the way back reads every home and repo write made while netbooted); /fast -> the SSD dir. On the way back the container still mounts its old /fast on the NV3, so /fast writes made while netbooted are NOT seen there unless the SSD dir is bind-mounted as the container's /fast (a host act, named for the owner, not tonight); until then the GPU jobs stay stopped while netbooted.

## RISKS
- A1 REACHABLE IS READ, NOT ASSUMED: every remote way back runs from encryption-town over the tunnel that lost its address 11-14 (cause still unknown, goal:g7.16.1.11.47). B4's positive read = a FRESH tunnel handshake for the PC seen from encryption-town plus one ssh command answered, within 15 min of the reboot; its absence triggers the way back. NOT READ: whether ANY remote power or reset path exists (a smart plug, a BMC; a consumer board has no BMC). If none, a netboot that hangs before the watchdog is armed, or a PC that never reaches the network, leaves the lab DOWN until the owner is home; this cost is named here before any reboot, for the council and the owner to weigh.
- S3 A HANG IS NOT A FAILED BOOT: neither the boot order nor a boot-once resets a box that booted and then hung. The chipset watchdog (READ: SP5100 TCO, 60 s, present) armed in the image's initrd and kept armed by systemd after boot turns a hang into a reset -> Bazzite. 'rig wake' (if wake-on-LAN) starts a box that is off, never a hung one.
- A2 THE WAY BACK BOOTS THE FAILING DRIVE: Bazzite and the container sit on the NV3 (belam's 11-10 read: ~1.04 M media/integrity errors, rising, spare 100%). SMART is read again in PHASE A; a failing-now read means the way back may not exist, so PHASE B waits for that read and the owner's word.
- Root over the network: NOT READ whether the NBD root rides the LAN or the tunnel. Over the tunnel, a link loss freezes the OS outright (worse than today's stuck NFS); the watchdog then resets to Bazzite.
- Rollback per step: A2 copy fails -> nothing changed. A3 image work fails -> nothing on the PC changed. A4 a boot_id changed with no owner restart cited -> STOP and report; nothing further. B0 the way back fails -> STOP: the rest of PHASE B is BANKED (the way back is not proven). B3/B4 fail -> 'rig boot gaming' remotely, else the watchdog's reset, else the owner's hand (the named cost). B5 red -> the way back; container crew restarted after the image crew is down.
