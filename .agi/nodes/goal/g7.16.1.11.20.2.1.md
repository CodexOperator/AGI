## Why this exists

Its drain keeps that promise by asking, before each send, whether the seat's own out-ref already carries the line's Alarm-id (already_sent). That guard assumes an id names ONE alarm. ## Target end-state
- An alarm's random id has 64 bits: `new_id` reads `secrets.token_hex(8)`, so two alarms to one reader in one second collide with probability about 2^-64 per pair and never in practice. The deterministic `--id` (same content, same id, by design) is untouched.
- A skip is never silent. When the drain skips a line because its Alarm-id is already on the seat's out-ref, it prints ONE line on stdout, the channel the `sent` line uses: `alarm_spool: skipped <id>: already on <seat>'s out-ref`. A true duplicate (a send whose unlink never ran) is still sent once and never twice, and now a reader can see it was skipped.
- `already_sent` tells 'not found' from 'could not read', in three cases. (1) The out-ref is ABSENT (`git rev-parse --verify --quiet <ref>` exits 1): NOT FOUND. The alarm is sent, and NO could-not-read line is printed (a seat's first alarm to a reader). (2) The ref exists and `git log` finds no Alarm-id: NOT FOUND, sent. (3) The ref exists but `git log` exits non-zero, or `rev-parse` exits with anything other than 0 or 1, or git cannot run (OSError, a timeout): COULD NOT READ. The line is HELD: it stays in the spool, the drain prints ONE line naming the ref and the cause (ONCE PER EPISODE, at the first hold after a read that succeeded, `holds == 1`, as the drain's own `tries == 1` notice does), and the next drain retries it. This is decided here, not left to the builder (alive 03:55:09Z): HOLD keeps 'a spool line is sent exactly once' true, and the cost is one drain's delay. A HOLD is NOT a send try: it is counted in its OWN counter, `rec['holds']`, and `rec['tries']` is untouched. `holds` is RESET to 0 when a read SUCCEEDS (`already_sent` finds the id or finds it absent), before the send, so each unreadable EPISODE prints its own line once, and the bound counts CONSECUTIVE unreadable drains, never drains added across episodes (self-perpetuating 04:12:03Z: without the reset a line held once, recovered with a failing send, then unreadable again, holds 2 and prints NOTHING, a silent hold). The hold is BOUNDED (aio 03:58:04Z): an unreadable out-ref is usually systemic, so an uncounted hold would repeat for ever, the spool would never empty, and `max_lines` would then refuse new appends. At `holds >= --max-holds` the line moves to `alarm.spool.dead` with its OWN notice `[alarm-unverified] <id> <job> -> <to>: out-ref unreadable for N drains, may or may not have been sent`, NEVER `[alarm-dead]` (that word is for a send that failed). `--max-holds` is OPTIONAL and defaults to `--max-tries`, so no cron row that passes only `--max-tries` changes.
- A spool line written before the change, whose id has the old width (8 hex, a dash, 4 hex), still drains: the id is an opaque string to the drain.

## Invariants

- The skip line and the could-not-read line carry the alarm id, the seat and the ref only. No alarm text, no token, no key.
- The drain's send path, its `tries` count and its `[alarm-dead]` path are unchanged for a SEND that fails. A HOLD is not a send: it leaves `tries` as it was, and only the `holds` bound writes the dead-letter file, with `[alarm-unverified]`.
- PRODUCT RISK, named: a line moved to `.dead` as unverified MAY have been sent (the out-ref could not be read, so nobody knows), and may not have been. That is why its notice says so, and why it is a different word from `[alarm-dead]`. The alternative, sending on could-not-read, can send an alarm twice.
