## OWNER 2026-10-06 (via plan-master), verbatim
Yes please. And the capsule does a watch for new messages automatically we just need to modify slightly how it delivers it. Make the mail delivery route be a part of the template for a raw shell post. It should just pop the mail into the tmux pane as plain text popping in or even doing a captive flow of mail arrived notification that pops up in the pane 'mail …' or 'box …' whatever the standard mail notification is would you like to read now? (Y/n) and the agent or internal subagent using it has to clear that manually. Sending y just runs the regular box read route with return printed into pane as just text outside shell entry.

## OWNER 2026-10-06 integrate (via plan-master), verbatim
It should all be integrated into graph and math base layer so it reprojects cleanly. This is where we lean on the council for the design work.

## Target end-state
- The raw-shell post template includes a mail delivery route.
- Capsule's existing new-mail watch is reused (no new watcher).
- On new mail, the tmux pane shows a standard notice (e.g. box: mail from <sender>, read now? (Y/n)) that blocks until answered by hand.
- Answering y runs the regular box read route; the result prints into the pane as plain text outside the shell prompt.
- Minimal and lean; no Python.

## Invariants
- Reuse capsule new-mail watch; delivery-path change only — no second watcher.
- Mail delivery route lives in the raw-shell post template (geometry), not ad hoc per seat.
- Captive Y/n must be cleared manually; y = existing box read; output is plain text in-pane, outside shell entry.
- No new Python; Master untouched; standard loop only.

## Falsifier
1. A CLI/grep that exits 0 only when a raw-shell template (or equivalent geometry cell) documents/implements the captive notice + y→box read path, and no second mail-watch process is introduced beside the capsule watch.
2. Negative: new Python mail watcher; auto-clear without Y/n; delivery that never prints box read output as plain in-pane text.
