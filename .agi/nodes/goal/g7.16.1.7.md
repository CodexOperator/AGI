## Target end-state
```
formation template (link rows -> null) ─ ONE activation ─▶ written into .geometry
   └─ stand-up fills each row: post template + customizations ─▶ harness template (+ its adapter map) ─▶ model row (default marker)
      walk: nearest wins · <= walk_max hops (a config cell, 5) · cycle guard · over the limit = ONE named simplify finding
post row = live cells (session id · pid · pane id) + mint-id LINKS (renderer · harness config · context docs · keys) -- never copies
```
- **ONE stand-up verb.** Spawn, rotate, heal recover and a hand restart are the same act (a rotation = a stand-up whose row links its predecessor). It runs self-activated in the background: the owner or the Prime activates a formation template and chains a harness template; nothing else is typed.
- **The first turn is a render, not a paste.** A stood-up post's first turn is a TOOL-CALL turn. One render call returns the graph slice of the post's linked context docs, including its live card and the active formation line, and that slice IS the tool result. It is the SAME render a human reads (goal:g2.19: one render, two readers), in the inline display mode (one block, the way fresh rotations read their docs today). The render pipeline also has a graphical mode, and more engine functions rest on it. Engine CLIs as tools/MCP come later: the internals first.
- **ONE pi harness template.** Its rows are JSON objects (model + thinking level, extendable to other harness settings) covering the internal aliases in use. Exactly one row carries the default marker, and any row can be chosen at stand-up or changed on the fly. There is no pi-free / pi-local pair.
- **The harness adapter map is the spine.** Every harness (Claude Code, pi, later third parties) ships a template mapping its actions and hooks onto the SAME four engine verbs: write · wake · render · stand-up. A message is a write (goal:g7.32.6), so there is no `send` verb, and no verb exists for one harness only.
- **A switch-over is atomic.** The new resolved config is written beside the old and ONE symlink rename swaps it; no reader ever sees neither.
- **Seat claiming needs no model act.** heal assigns a post's keys from a key template (kind and forgiving in season 2), and a key row lands on the post's own trunk too, never on one trunk alone.
- **The guard is in the graph** (landed 09-30 by the Prime: guard-init.sh, sanctuary-health, sanctuary-watch and GUARD.md as build nodes, guard.env as config:guard). Its settings are keyed by the logical BOX name (guard.md:25, AGI_BOX), never by host name.
Every engine event reaches a post through its pane: goal:g7.16.1.7.3 (the magic pane, owned by the post ROW and handed across rotations; renumbered from g7.16.1.9, council 01:3xZ 09-30).
Nested: goal:g7.16.1.7.1 (7a NOW: the stand-up verb, the first-turn render, the pi template, heal keys) · goal:g7.16.1.7.2 (7b AFTER goal:g7.16.1.6 + goal:g4.18.6: the walk, the swap, one resolver, the post row as links, formations as templates). Targets no leaf carries yet, to sketch as leaves when their dependency lands: the harness adapter maps (the spine) · the render display modes · context docs linked from the post row.

## Invariants
- A template field lives in ONE node; everything else links to it by mint id.
- A live post is never without a readable config (the swap is atomic) or without a key it can sign with.
- No model, effort or harness literal lives in a launch path; the walk is the only resolver.
- Templates only get simpler: an override equal to its inherited value is refused, so customizations never accrete, and a chain needing more than walk_max hops is ONE finding to simplify, never a limit to raise.
- A post is addressed by its ROW, resolved to its live cells (pane id, pid) at the moment of use, never through a cached pid or pane (owner 06:0xZ 09-27: "pids rotate but tmux panes stay the same"; goal:g7.32.6's wake cites this).
- A post row never claims a life it does not have: the verify pass cross-checks its session id, pid and pane, and a row pointing at a dead process is ONE finding naming the row, never a stale row the next stand-up trusts.

## Falsifier
1. From a formation template, ONE activation stands up its posts, and each post row afterwards holds session id, pid and pane id plus mint-id links (not copies) to its harness, model, renderer and context docs.
2. A post's first turn is a tool result whose body is byte-identical to `viewport.py --emit llm` for that post's links.
3. COLD START: a fresh clone on a scratch box plus ONE formation activation gives a running formation, with nothing else typed.
4. Switching a live post's model is one row change in the harness template (or one post-row link change) plus the atomic swap, with no restart of any other post.
5. Negative: 0 pi-free / pi-local template pairs · 0 model or effort literals in rotate.py / heal.py launch paths · 1 resolver where there were 5 · a 6-hop template chain yields exactly ONE named finding.
