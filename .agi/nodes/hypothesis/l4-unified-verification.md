# hypothesis:l4-unified-verification

## Hypothesis

What is the testable claim? What would prove it? What would disprove it?

<!-- THOUGHT:BEGIN — authored, not derived; carried across regenerating scans. The reasoning behind THIS version. -->
THE OWNER ASKED FOR A TOOL AND THE RISK IS THAT THE TOOL BECOMES THE THING IT REPLACES. Four prose copies of the standard commands drifted apart, which is why `goal:g1.10` moved them into `command:commands` and gave them one resolver. A `verification.py` that opens with its own list of argv would be a fifth copy — and the worst one, because it would be the copy every successor actually runs and therefore trusts. So the claim is written so that the resolution requirement, not the level menu, is what decides the round: if any declared argv appears literally in the new file, the round is disproved no matter how green its tests are. A check that is genuinely new gets DECLARED in the node and resolved like the rest.

THE COUNT CHECK IS THE ONE I ALMOST WROTE WRONG. "The active count must not drop" reads like a check and is not one — smoke PRINTS counts, and printing a number nobody compares is exactly the shape of gen II's second miss, where a test's NAME stood in for the invariant. A drop is the failure this repo has already paid 29k nodes for (H0/H0b). So the file has to hold a baseline and FAIL below it; anything less is a tool that would have watched that data loss happen and exited 0.

WHY `--suite` IS OPT-IN RATHER THAN PART OF `full`. The owner said "a full thorough check each rotation", and the literal reading puts pytest in `full`. But the suite window is the Prime's to grant, one runner at a time, and `test_send.py` nudges real tmux panes until L4.10 lands. A verification tool that takes that window unasked converts a safety check into a scheduling conflict, and the first successor to run `--level full` innocently would collide with whoever else was running it. Opt-in keeps the owner's thorough check available in one flag without making it a trap. Recorded as a deviation from the literal ask, with the reason, per the delegated-authority terms.

WHY THIS ROUND DOES NOT TOUCH `rotate.py`, WHICH REVERSES THE ORDERING I INHERITED. Gen II handed me L4.44 held behind L4.45 because "both touch rotate.py". I checked instead of inheriting: `grep -n "links.py|snapshot-goals|write_guard|driver.sh|pytest" extensions/agi/bin/rotate.py` returns NOTHING. The four-tool list a successor runs lives at `extensions/agi/briefs/prime-director-successor.md` line 7, which `rotate.py` only reads through `_successor_command`. The premise of the hold was wrong, so the hold is not required — but rather than rely on that reasoning holding for the kid too, the claim FORBIDS touching `rotate.py` and `cli.py` outright and tells the kid to stop and report if it thinks otherwise. That converts an ordering assumption into an enforced boundary, which is the version that survives being wrong.

NAMING. `verify_unified.py` already exists and is the `goal:g11` migration checker. `verification.py` beside it is one keystroke away from a genuinely dangerous confusion, and I am keeping the owner's name rather than inventing a better one, because the owner names files and successors read owner text. The mitigation is in the docstring requirement instead: the first paragraph has to say which is which.
