# hypothesis:a00-237fbea7-78b6c7

## Hypothesis

A single Grok adapter can expose pane operations as optional, feature-detected methods while preserving the required g7.25 surface; harnesses that do not hold a named pane should remain valid and use the non-pane path.

## Minimal experiment

Add or identify one adapter object exposing `build_command` plus optional `pane_attach`, `pane_send`, and `pane_read`. Exercise one pane-backed instance and one pane-free instance, then call an optional method without a held pane.

## Proof criteria

- There is still exactly one Grok adapter module; no `grok_pane_adapter.py` appears.
- A pane-backed adapter delegates pane operations to the existing g7.31.1 hold without taking ownership of it.
- A pane-free harness feature-detects the missing methods and continues on its non-pane path.
- Calling an available pane method without a held pane raises a named, bounded error rather than hanging or silently inventing a pane.

## Disproof criteria

- Pane support requires a second adapter type or module.
- `dispatch.py` or `rotate.py` needs a Grok-name branch.
- Optional-method absence makes a pane-free harness invalid.
- Missing hold state produces a hang, a silent no-op, or an unnamed exception.

## Status

This node states a testable design contract only; no implementation or experiment was run in this round, so the claim remains pending measurement.
