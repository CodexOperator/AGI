# hypothesis:a00-2001b96e-f193e1

## Hypothesis

A held grok-bot seat's pane child runs with an environment EXACTLY equal to
the scrubbed `child_env` the direct `Popen` path uses -- no variable the tmux
SERVER carries can leak into it, even when that variable was removed from the
passed `env`. And a tmux that is PRESENT but broken (any `OSError` that is not
`FileNotFoundError`) is a NAMED `PaneHoldError`, never an anonymous `Popen`
fallback.

**Why this replaces kid-2's claim.** Kid-2 threaded the env as
`tmux -e NAME=VALUE`, but `-e` only ADDS an override to the tmux server's
environment; it can never REMOVE one. A runtime `OPENROUTER_API_KEY` the server
already carries therefore still reached a `needs_credential=False` seat, and
`drop_unneeded_credential` was lost. The claim is now carried by a mode-0600
launcher running `exec env -i K=V ... <argv>`.

## What would prove it

On REAL tmux, with the tmux server deliberately seeded with a sentinel: (a) a
pane launched by `restart(hold_pane=True)` must show the scrubbed marker but
NOT the sentinel in its own `env`; (b) an `env=None` control must show the
sentinel (non-vacuity); (c) `PermissionError` from tmux must raise
`PaneHoldError` with no `Popen`. Plus the kid-1/kid-2 regressions stay green
(one `new-session` then one `respawn-pane` at the same name; C/D named).

## What would disprove it

The pane child's own `env` still contains a variable removed from the passed
`env`; or a present-but-broken tmux silently yields an anonymous `Popen`; or
any of the four named test files goes red.

## Result

Proved on real tmux 3.4. Evidence and the five negatived falsifiers live in
child `experiment:a00-2001b96e-real-tmux-pane-env-exact`.
