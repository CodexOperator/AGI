# hypothesis:a00-4841914f-4c6e6d

## Hypothesis

The held restart path should use the same adapter environment seam as the
ordinary spawn: compute `child_env(...)` before returning the held pid, and
thread that environment into `tmux_hold` when the pane is created or
reattached. In particular, a credential-none row must not regain
`OPENROUTER_API_KEY` merely because restart was held.

## Testable claim

Given a fake adapter whose `child_env` returns a sentinel environment, calling
the held restart path must (1) call `child_env` and (2) pass the resulting map
to the `tmux_hold` start/reattach operation. With a credential-none harness and
an inherited `OPENROUTER_API_KEY`, the held pane environment must omit that
key; a default/needs-credential row must retain it.

## Evidence and falsifiers

A unit test with spies around the adapter and hold implementation would prove
the claim if it observes the sentinel environment at the hold boundary and
checks both credential modes. It would disprove the claim if held restart
returns before `child_env`, reconstructs environment from bare `os.environ`, or
leaves `tmux_hold` to inherit the server environment. The current test suite
already proves the ordinary `pi.restart` path, so this hypothesis isolates the
held branch rather than re-testing that seam.
