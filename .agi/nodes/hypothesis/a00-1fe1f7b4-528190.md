# hypothesis:a00-1fe1f7b4-528190

## Hypothesis

The prior round closed the mechanics (`pane_hold.ensure_pane` survives a
SIGKILL with the same `%N`; `restart` reuses it) but its real-tmux test
HAND-INJECTED `record = {"pane": "seatA"}`. Nothing in `dispatch.py`,
`rotate.py`, `heal.py` or the adapter's first spawn ever set that field, so
in production there was no pane to reattach to and the opt-in was
unreachable.

Claim: a GENERIC, harness-agnostic pane opt-in — a `harness["pane"]` cell
read by the adapter's own first-spawn lifecycle entry — creates the named
tmux pane, stamps `pane` / `pane_session` / `pane_id` onto the agent record
itself, and leaves `restart` resolving the same name through one helper, so
killing the seat then restarting reattaches to the SAME `%N` (new
`pane_pid`) with NO hand-injected record field.

**Prove:** spawn through the adapter lifecycle with a record carrying no
pane field; assert a live named pane and a stamped record; SIGKILL; restart;
assert same name, same `%N`, new `pane_pid`, alive window.

**Disprove:** spawn leaves no record pane, `restart` cannot find a pane, or
the name/`%N` changes across the kill. Also disproven if the wiring needs a
harness literal in `dispatch.py` / `rotate.py` or a second argv builder.

**Scope note (named residual):** dispatch's live spawn still Popens directly
in `_open_round`, so `--persistent` production rounds are not yet born inside
a pane; the adapter seam they must adopt now exists and its remaining
integration is recorded on the experiment node.
