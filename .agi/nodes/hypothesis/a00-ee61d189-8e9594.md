# hypothesis:a00-ee61d189-8e9594

**Claim.** The DELIVERY leg of `send.py` -- where a message's bytes finally
land -- is chosen from a runtime-extensible table (`DELIVERY_TRANSPORTS` +
`register_delivery`), so a genuinely new transport is a new module + a table
row, never a new `if` inside `send()` / `send_dm()`. Two delivery points
consult it: `send()`'s inbox append (kind `file`) and `send_dm()`'s pane wake
(kind `nudge`). The built-in row is the default.

**Prove it.** Register a NEW delivery transport at run time (priority=1)
without editing `send.py`'s selection loop and observe `send()` hand the
block to IT instead of writing the inbox file, and `send_dm()` hand the dm
body to IT instead of calling the pane. A row that returns False must fall
through to the built-in; with nothing registered the bytes on disk must be
unchanged.

**Disprove it.** Delivery is still chosen by an inline `if`/`open()` inside
`send()` or `send_dm()`, or registering a transport changes the bytes the
default path writes.

*addressing* (room / dm / inbox); `DELIVERY_TRANSPORTS` decides the *final
hop* of the bytes once the verb is chosen. Two decisions, two tables; the
CLI table's order is untouched.
