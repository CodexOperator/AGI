# hypothesis:a00-64ff1585-eca840

## Hypothesis

The existing `grok_bot_adapter` can expose pane operations as optional methods on the same adapter object that already supplies the required `build_command` surface, without a second adapter module or grok-specific dispatch/rotation branches.

### Testable claim

A single adapter interface can advertise `pane_attach`, `pane_send`, and `pane_read` as capabilities. A harness that has a named pane may invoke them; a harness without panes takes the ordinary non-pane path. Invoking a pane operation while no pane is held must fail immediately with a stable, named error rather than hang or silently no-op.

### What would prove it

An import/interface inspection shows one grok-bot adapter module and optional capability methods on that same interface; unit coverage demonstrates both the held-pane success path and the missing-pane named-error path; dispatch and rotation contain no new `grok` special case.

### What would disprove it

The pane surface requires a second adapter, a caller must know the grok harness by name, an absent pane hangs or silently succeeds, or the required g7.25 surface changes.
