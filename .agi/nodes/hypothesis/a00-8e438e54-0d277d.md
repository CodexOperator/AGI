# hypothesis:a00-8e438e54-0d277d
## Hypothesis

On a durable named tmux-pane **hold restart** (grok-bot seat,
`goal:g7.31.1.2`), the environment the restarted seat process actually runs
under is exactly what the adapter's `child_env()` builds: `harness["env"]`
literals applied, `harness["forward_env"]` names forwarded, and the
credential-none key (`OPENROUTER_API_KEY`) dropped — NOT the tmux SERVER's
inherited environment.

**Prove:** a sentinel var that only `child_env()` adds is read back from inside
the respawned pane process (a harness env literal is decisive, because it is
by construction absent from the server env), and a key `child_env()` drops is
absent from the pane even when the tmux server's env carries it.

**Disprove:** the pane's `/proc/self/environ` lacks the sentinel, or carries
the dropped key. In the unmodified bytes it did: `reattach` took no `env` and
`restart`'s hold branch never called `child_env()`, so `respawn-pane` injected
the tmux server's frozen env (measured — see
`experiment:durable-hold-preserves-child-env`, `RESULT sentinel_present_in_pane
= False`). The fix threads `env` through `tmux_hold` as `env -i K=V ...`, so
the pane env is replaced rather than merged; the post-fix live probe passes
both conjuncts.
What is the testable claim? What would prove it? What would disprove it?

## Agent Notes
Live tmux probe: unmodified bytes dropped child_env on hold restart (sentinel absent from pane; tmux server env won). Fixed by threading child_env through tmux_hold as 'env -i K=V ...' on respawn-pane, replacing (not merging) the server env so the credential-none drop survives. Post-fix production grok.restart probe: set key reads child_env value, dropped key absent. 67 tests pass; 30 prod lines, ceiling 40.
