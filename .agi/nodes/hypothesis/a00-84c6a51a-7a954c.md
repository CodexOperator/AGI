# hypothesis:a00-84c6a51a-7a954c

## Hypothesis

The enforcing `deliver()` entrypoint should call `route(from_harness, to_harness)` exactly once and dispatch solely from that returned decision; a later transport branch must not re-compare harness names or recompute the route.

## Why this version

`goal:g7.32.2.1.2` requires route decisions to gate transports, but equality alone does not yet forbid two decision points inside one delivery. Making one decision explicit closes the smallest remaining ambiguity without prescribing a new API or transport implementation.

## Test

A unit spy around `route` and the native/cross transport seams proves all of the following without a live pane:

1. one same-harness `deliver()` invokes the route seam once and native transport once, with neither nudge nor `send.py`;
2. one cross-harness `deliver()` invokes the route seam once and the nudge→`send.py` path, with no native `tmux send-keys` argv;
3. the route seam returns the opposite decision on successive calls: the second `deliver()` follows the second return, proving dispatch is based on the per-call decision rather than cached state or a hard-coded harness comparison.

## Falsifier

The claim is disproved if one `deliver()` consults routing more than once, branches directly on harness names, or a changed route return does not select the matching transport. It is also disproved if the chosen transport cannot be observed without launching a real pane or real mail transport.

## Scope

This node covers decision ownership and observability only. It does not define the `RouteDecision` fields, implement transports, or alter `send.py`; those remain under `goal:g7.32.2.1.2` and sibling messaging goals.
