# hypothesis:a00-73fb563e-6ccb33

## Hypothesis

A Grok seat can gain pane messaging without a second adapter by adding optional module-level capabilities (`pane_attach`, `pane_send`, and `pane_read`) to the existing `grok_bot_adapter`, while every pane method resolves the seat's already-held named pane through one explicit hold lookup and raises a named `PaneUnavailable` error when no hold exists.

## Why this shape

The live adapter is a module, not an object instance, and currently owns only the five REQUIRED spawn functions. Treating pane methods as ordinary optional module functions therefore adds capability without changing `adapters.REQUIRED` or teaching non-Grok adapters a no-op interface. An explicit hold lookup preserves `goal:g7.31.1` ownership: the pane methods consume a hold, never create, replace, or release it.

## Testable claim

A focused test can demonstrate all of the following without tmux or a live Grok process:

1. `adapters.load("grok_bot")` still satisfies `adapters.REQUIRED` and the three pane functions are callable optional attributes.
2. With a fake held pane, each optional method delegates to that same pane and forwards its operation arguments.
3. With no hold, every optional method raises `grok_bot_adapter.PaneUnavailable` naming the missing seat/pane, rather than blocking or returning a success-shaped value.
4. Pi, Claude Code, and Copilot adapters do not expose the Grok pane methods, and `dispatch.py` / `rotate.py` contain no new Grok-specific branch.

## Falsifier

- A second `grok_pane_adapter.py` or another harness-name branch is needed.
- Optional methods must mutate the REQUIRED interface for every harness to remain loadable.
- Pane state is duplicated inside the adapter rather than referenced through the existing hold owner.
- Failure without a hold can hang, silently no-op, or report success.

Implement the smallest test seam around hold resolution and optional delegation, then run `extensions/agi/tests/test_grok_bot_adapter.py`. This node is a design claim; the experiment should establish whether the current module/hold representation supports the shape before any real tmux transport is added.
