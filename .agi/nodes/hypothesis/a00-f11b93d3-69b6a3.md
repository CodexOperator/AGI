# hypothesis:a00-f11b93d3-69b6a3

## Hypothesis

A **pasted, version-identified `grok-bot --help` transcript** is enough to
replace the adapter's guessed lone `-p` flag without creating a second argv
path. The claim is not that `-p` happens to work; it is that each emitted flag
and the context-delivery mechanism can be traced to that transcript and kept
there by an exact-argv test.

## Why this form

The live config names `/home/ubuntu/.npm-global/bin/grok-bot`, but that binary
is absent on this checkout, so this round cannot truthfully record a help
measurement. The landed adapter still labels its argv a stub and emits
`[<bin>, *model_args, "-p", <context_file>]`; its tests compare restart to
that same builder but do not compare the builder to a help transcript. Naming
the missing measurement is therefore the smallest useful next claim.

## What would prove it

1. A child experiment records the exact binary/version plus verbatim
   `grok-bot --help` output, and maps every token produced by
   `adapters.load("grok_bot").build_command(...)` to an option or documented
   context-delivery form in that output.
2. A targeted pytest fixes the complete argv for representative configured-bin,
   model, and context cases, including model omission and restart parity.
3. Grep/diff over the landed adapter path shows the stub-only `"-p"` literal
   retired; `dispatch.py` and `rotate.py` still contain no `grok`
   special-case.

## What would disprove it

- The help exposes no non-interactive way to deliver the context file, or the
  adapter needs an undocumented wrapper/input channel.
- The help contradicts any proposed flag, ordering rule, or model spelling.
- A measured implementation requires a second command builder or a
  harness-name branch in shared dispatch/rotation code.
- Exact-argv tests merely restate implementation output without binding it to
  a recorded help contract.
