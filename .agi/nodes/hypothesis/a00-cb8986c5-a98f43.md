# hypothesis:a00-cb8986c5-a98f43

## Hypothesis

The durable-pane guarantee can remain small and adapter-agnostic if the
persistent-seat launch seam returns one launch outcome: the successfully held
pane's id plus `created` based on what actually happened. `dispatch._open_round`
should consume that outcome only after the hold succeeds; restart should consume
the recorded pane id rather than deciding whether a pane was created. A failed
hold must not leave a fabricated or stale pane identity in the dispatch record.

This sharpens the pending sibling `hypothesis:a00-518fd475-34ba25`: that node
identifies the bypass in `_open_round`; this node tests the boundary that makes
one implementation serve both first spawn and restart.

## Test

With a fake persistent adapter and fake hold seam, exercise the production
launch wrapper used by `_open_round`:

1. a successful first hold records exactly the returned pane id;
2. restart passes the recorded id and does not choose or report a new one;
3. a hold failure records no pane id and does not report `created=true`;
4. a later successful restart records the hold result's real `created` value.

No live tmux or real process is needed; the test boundary is the return value
crossing from the hold seam into dispatch's persisted launch record.

## Falsifier

The claim is disproved if production launch records a pane before the hold
returns, if restart can fabricate `created=true` after a failed or bypassed
hold, or if a successful hold's returned pane id is not the id persisted and
reused. A counterexample is stronger if the same fake-adapter scenario passes
only by calling the hold seam out of band.

## Scope

This node makes no claim about tmux naming, UI, or exact adapter commands. Its
only testable claim is that a successful/failed launch result is the single
source of truth for pane identity and `created` on both initial launch and
restart.
