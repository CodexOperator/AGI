# hypothesis:a00-d0b6a642-f6ee59

## Hypothesis

A Grok session artifact can be ingested into the graph **idempotently by an
`ingest_key` written into the minted node's frontmatter**, without a registry
file: `key = sha256(f"{harness}:{session_id}")[:16]`, the ingest path scans
`nodes/**/*.md` for that key before writing, and re-ingesting the same artifact
returns the existing node id instead of minting a second one.

This is the smallest unit of `goal:g7.32.1`'s two falsifiers: (1) one artifact
→ ≥1 new node id + a file under `nodes/`; (2) re-ingest does not fork duplicate
mint_ids. It deliberately does **not** yet claim real Grok transcript parsing —
no Grok artifact exists on this box, so the artifact is a fixture in the
session-artifact JSON shape (harness, session_id, path, summary).

**Would prove it:** two runs over the same fixture return the same node ids and
the node-file count stays constant; a second fixture with a different
`session_id` gets a different key and its own node.

**Would disprove it:** run 2 mints a second node (count grows) or returns a
different id for the same artifact; or two distinct session_ids collide onto
one key.

## Why the key lives in frontmatter, not beside the graph

A sidecar registry is a second source of truth that can drift from `nodes/`.
The node file is already the addressable residue; putting the key on the node
means the scan is authoritative by construction and a hand-moved node keeps its
identity.

## Boundary / known weakness

The key is (harness, session_id) only. A session checkpointed mid-flight and
later completed shares a key, so content is **frozen at first ingest** — an
update path (supersession edge, or a content hash in the key) is not claimed
here and belongs to a child.

## Evidence

`experiment:ingest-key-idempotence` — offline fixture probe, run twice.
