# hypothesis:a00-53cfda35-ceb961

## Hypothesis

**The first-spawn pane defect is a missing adapter launch seam, not a missing
first-spawn special case.** If every persistent adapter exposes one
`launch(..., record=None)` operation and both `dispatch._open_round` and
`adapter.restart` call it, the first process and every restart are governed by
the same tmux-hold implementation. A Grok-specific `if` in `dispatch.py` is
then unnecessary and cannot make restart and first spawn drift again.

## Why this version

Inspection of the live checkout shows production first spawn is currently a
direct `subprocess.Popen` inside `dispatch._open_round`. The restart contract
is delegated to `adapter.restart`; `grok_bot_adapter.restart` also directly
calls `Popen`. Thus the named-pane capability, wherever it already lives, is
not on the production first-spawn path. Restart alone cannot establish the
parent goal's stable `pane_id` invariant.

The smallest testable seam is an optional adapter capability (for example
`launch`), not a required interface expansion: ordinary pi and Claude Code
adapters should retain direct `Popen` behavior. Only a persistent adapter opts
into pane launch. This preserves the existing adapter contract while making
the persistence decision adapter-owned.

## Probe design

Use a fake persistent adapter and substitute subprocess/tmux seams; do not spawn
a real model.

1. Call production `dispatch._open_round` for the fake adapter.
2. Assert the first call asks the adapter launch seam for a stable pane id and
   writes that id to the new `agent.json`; assert no `created=true` is
   fabricated before the hold layer observes the pane.
3. Kill the represented process and call `adapter.restart` with that record.
4. Assert restart asks for the same stable pane id and never overwrites it
   with a newly fabricated identity.
5. Negative control: the pi adapter still calls its direct process-launch path
   and adds no pane metadata.

## What would prove it

The probe passes all five checks on production code: first spawn and restart
both traverse the same optional persistent-launch seam, the pane identity is
unchanged across simulated `kill -9`, and non-persistent adapters are unchanged.

## What would disprove it

Any one of these falsifies the claim: first spawn still reaches direct `Popen`
for the persistent adapter; restart uses a different launch implementation;
the first restart replaces the recorded pane id; `created=true` is stamped
without a hold observation; or adding the seam changes a non-persistent
adapter.

## Scope and next edge

This node claims only the seam and identity invariant. It does not claim that
the tmux implementation survives a real `kill -9`; that is the experiment's
separate live-tmux falsifier. If proved, spawn an experiment implementing the
optional capability and then an MVP that routes both call sites through it.
