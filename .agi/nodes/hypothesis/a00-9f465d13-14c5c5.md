# hypothesis:a00-9f465d13-14c5c5

## Hypothesis

A small transport registry can make `send.py` a thin chooser without moving authorization or message semantics into the router: policy stays in the existing seatsig/box/audience modules, while the registry rows only map a delivery target to a transport callable and its arguments.

## Test

A build would be supported if it can add a transport by adding one module plus one registry row, and if tests show:

1. the router does not import `rotate` or `dispatch` orchestration;
2. forged/retired/audience refusals are unchanged and are raised by policy modules rather than selected by transport rows;
3. native, signed DM/board, and cross-harness nudge paths produce the same externally visible message and state transitions as before;
4. wrap/peek remains a read/presentation operation and creates no delivery route.

## Falsifier

The claim fails if transport selection still needs harness-specific branches in `send.py`, if extracting a row changes any refusal or message bytes, or if a new transport necessarily imports formation/rotation policy to dispatch.

## Narrow implementation seam

Keep message serialization, signing, inbox/room persistence, and audience checks out of the registry. Represent only transport capability and dispatch. This is deliberately a claim about a seam, not a mandate to rewrite the current 5,000+ line module in one iteration; the first build should extract one path behind an adapter and leave compatibility wrappers in place.
