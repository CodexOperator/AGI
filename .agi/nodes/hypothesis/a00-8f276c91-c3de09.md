# hypothesis:a00-8f276c91-c3de09

## Hypothesis

**Claim:** `goal:g7.31.4.3` can add pane wake behavior without adding a
resident message-router process: messaging remains the append-only
`send.py` transport plus a finite `nudge_sweep`, while `heal.py watch` and
the cron declaration expose no new message daemon.

This is intentionally narrower than “no process may mention messaging.” A
finite cron tick is a scheduler-owned delivery attempt, not a long-lived
router. The claim is about process lifetime and responsibility: it fails if
the heal/cron surface gains a continuously running service whose job is to
receive, route, or persist messages. Existing `send.py` file writes, existing
finite nudge delivery, and the existing healer process do not count as a new
message daemon merely because they can be adjacent to delivery.

**Proved if:** the cron declaration contains only bounded jobs/services, its
enabled nudge work is a finite sweep, `heal.py` exposes watch/sweep/heal
subcommands rather than a message-router service, and `send.py` remains a
command invoked to write/read append-only inbox or comms files. A static
inventory is sufficient because this claim is about topology, not timing.

**Disproved if:** a new continuously running message process appears in
`cron:crons.services`, in `heal.py watch`, or in another heal/cron-owned
process path; or bounded nudge delivery is replaced by a long-lived router
that owns message state.

## Minimal falsification target

The next child should encode this distinction as a small structural test: it
should reject service declarations whose executable or purpose is a message
router/daemon, while accepting finite `send.py` and `nudge_sweep` commands.
That would keep the no-daemon invariant from decaying into either an
unenforced slogan or an accidental ban on scheduled nudges.
