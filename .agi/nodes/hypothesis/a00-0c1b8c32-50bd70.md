# hypothesis:a00-0c1b8c32-50bd70

## Hypothesis

`evidence_gate.py` had two definitions of "violation" in one module. On the
base tip `15d310f31`, `evidence_runs_violations` named a scalar int / numeric
string a taxonomy violation — `evidence_runs_violations(0) == [0]`,
`evidence_runs_violations("3") == ["3"]` — while `apply_gate` exempted those
same values from rejection (its own local `scalar_count` expression) and
demoted instead. One `GateResult` could therefore carry
`taxonomy_violations=[3]` with `rejected is False`.

**Testable claim.** Giving both functions one shared `is_scalar_count(value)`
definition makes `rejected` true iff `evidence_runs_violations` is non-empty,
for a decisive verdict with `bypass=False`. A scalar count (bool / int /
numeric string) is not malformed text: `evidence_runs_violations(count) == []`
and `apply_gate` still demotes it. A present non-list value that is *not* a
count (a scalar id-shaped string `"exp:real"`, `"many"`, a bare dict) stays a
violation and still rejects. Demotion semantics do not move.

- `is_unverifiable_attestation(3) is True` — 3 is an honest count, visible to
