# hypothesis:a00-de7ef533-6c07e5

## Hypothesis

**One adapter can carry pane capabilities without making pane support mandatory.**

`grok_bot_adapter` will retain its existing required adapter surface and add pane operations as an opt-in capability on that same module/interface. A pane-capable harness will expose `pane_attach`, `pane_send`, and `pane_read`; a harness without a named pane will not need those methods. Calls made on an adapter whose pane capability is unavailable will raise a named, fail-closed error rather than hang or silently create ownership of the pane.

### Prove

1. Unit tests load the existing Grok adapter and still validate every required g7.25 method.
2. A pane-capable fixture exposes all three methods through the same adapter object; a non-pane fixture passes the non-pane call path without importing a second `grok_pane_adapter.py`.
3. Calling a pane method without a held named pane raises the named error immediately.
4. The import graph contains only one Grok adapter module, and `dispatch.py` / `rotate.py` gain no `grok` special case.

### Disprove

Any design that requires a second parallel adapter, makes pane methods part of every harness's required surface, hides pane capability behind a `grok` name branch in dispatch/rotation, or can block/fail ambiguously without a held pane.

## Scope

This names the testable interface boundary only. Hold creation and lifetime remain owned by `goal:g7.31.1`; messaging product behavior remains in `goal:g7.32.2`; transport routing remains in `goal:g7.32.4`.
