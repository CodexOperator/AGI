# hypothesis:a00-1ea3e5cb-5d75a8

## Hypothesis

A real `dispatch --persistent` round can be born inside a durable NAMED tmux
pane, and the persistent supervisor's `reopen` reattaches to that SAME pane
name and `%N` (with a new `pane_pid`) after the seat process is killed --
without a harness literal in `dispatch.py`/`rotate.py`.

This is the residual `experiment:a00-spawn-pane-hold` named: the adapter seam
(`grok_bot_adapter.spawn` / `pane_hold.ensure_pane`) existed and reused `%N`,
but nothing in production called it. `dispatch._open_round` built a raw
`subprocess.Popen`, and the `grok-bot` config row had no generic `pane` cell,
so there was no pane to reattach to.

**Would prove it:** real `dispatch.main()` with `pane: true` creates a named
window; SIGKILL the seat; the supervisor restarts into the SAME `%N` with a
new `pane_pid`; the manifest record carries `pane`/`pane_id`/`pane_session`.

**Would disprove it:** no pane is born, the `%N` changes across restart, the
supervisor cannot poll a pane-backed handle, or a grok literal is required in
dispatch to make it work.

## Method

`_open_round` prefers a generic `adapter.spawn(...)` when the adapter exposes
one, handing it the already-rendered `argv`/`env`/`cwd`/`log_file` (one argv
path). The adapter returns a Popen-compatible `pane_hold.PaneProc` (`int` pid
+ `.pid`/`.poll()`/`.returncode`), so `spawn_budget.commit`, `_await_startup`,
`_supervise_persistent` and the reaper are untouched. Every adapter without
`spawn` keeps the byte-identical `Popen` branch.
