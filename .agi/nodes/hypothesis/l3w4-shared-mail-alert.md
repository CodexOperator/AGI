## Agent Notes
BUILD, NOT A PROBE. Owner ask (item 62, verbatim via belam): agents need a shared side-channel alert so they stop brute-forcing each other's attention via pane injection (user sends impersonating the owner). Two live incidents this session: master-sensei's DM to belam sat unread until the owner noticed in chat; the owner's own audience-quorum request sat unread until belam manually relayed it. THE FIVE CONSTRAINTS, owner's own words via belam, not negotiable in substance though the shape is yours: (1) no agent-side polling -- an agent must never spend a turn checking its own inbox; the injection has to arrive for free at a seam the harness already visits. (2) survives the recipient being mid-turn -- nothing is lost if the seam is busy, it just fires at the next one. (3) distinguishable from the owner -- a seat must always be able to tell another-agent-needs-me from the-human-is-talking-to-me. (4) leaves a record that an alert was raised and when -- never got it and ignored it must stay distinguishable failures. (5) one mechanism for dm, room and audience alike, not three. SUGGESTED SHAPE, yours to refine or replace: a new hook script under extensions/agi/hooks/ (silent no-op outside an agi project, same contract cc-session-start.sh already has), registered on UserPromptSubmit (fires every turn, unlike SessionStart which fires once -- quorum seats are long-lived), that calls send.py's existing rooms(croot, me) for dm+room unread counts plus whatever the plain inbox path needs for the same, and on nonzero unread prints a small system-reminder-tagged injection block (same shape CC hook output already takes) naming the room/sender and how long it's waited. Stamp alerted_at per seat+thread (a small state file is fine) so constraint 4 holds. INTEGRATION REQUIREMENT, from belam directly: rotate.py alarms already DMs a seat when its rotation meter is due, on a 300s loop, and has NEVER been switched on -- wiring it without this alert channel existing first would be a fourth instance of the same built-never-wired pattern already found three times today (this mechanism, failures.py, the seat-pin guard). Make alarms' rotation-due DM one of the live payloads this channel is proven against. SCOPE: this touches send.py (read-only use of existing functions, ideally no changes needed there) and a NEW hook script plus its settings.json registration. Do not touch seats.md. Do not touch moral:*. If registering globally in ~/.claude/settings.json feels wrong for blast radius, a project-scoped .claude/settings.json is the safer default -- your call, say which and why. PROVE: a test with a seat holding unread mail (dm, room, and inbox if that path is separate) asserting the hook's stdout contains the injection block and a clean seat asserting it does not; then one live check -- have this agent's own parent verify ITS OWN next natural seam shows nothing (clean), then have a kid send it a dm and confirm the NEXT seam shows the alert. Report struggles/caveats honestly if the live half can't be exercised in one round -- an honest inconclusive_lean_proved beats a claimed proved with no live check, this session has three examples of exactly that mistake already.

Supporting research, not a probe of this hypothesis (does not touch its testable_claim): before all-is-one landed on the hook approach, alive investigated whether SendMessage/ListAgents (Claude Codes native cross-session tool) could be called directly from send.py as an alternative delivery path. Confirmed via claude-code-guide: no. SendMessage is a model-side tool usable only from within a live agent turn; the CLAUDE_CODE_MESSAGING_SOCKET/TOKEN pair a session exports is scoped to that sessions own hooks/children, not reachable from outside or from another session. No CLI or hook path exists to push a message into an arbitrary other session. This is exactly why the hook-based PULL approach (a seat check its own mail at its own seam) is the right shape instead of a cross-session PUSH -- recorded here so nobody re-tries the SendMessage direction without knowing why it was ruled out.

CRITICAL GAP FOUND before registering (all-is-one, 2026-09-08, reviewing Q.05/a00-0058b6ec's accepted build). mail_alert.py resolves the current seat via send._detect_sender(None), which reads AGI_AGENT_ID -- and that env var is set ONLY for dispatched sub-agents (dispatch.py exports it at spawn time), NEVER for an interactive top-level session (a director or quorum seat's own Claude Code terminal). Confirmed by checking my own environment directly: no AGI_AGENT_ID, no AGI_SEAT, nothing send.py's identity resolver reads. Running the hook raw in my own interactive shell correctly and honestly falls back to seat='unknown' (send._detect_sender's documented behavior, hypothesis:l3-agent-id-never-exported -- deliberately never trusts a tmux window name as identity, for good reason, so this is not a bug in THAT function). THE CONSEQUENCE: as built, the hook helps a DISPATCHED kid or parent (which do get real identity) but does NOTHING for the exact case that motivated this whole hypothesis -- master-sensei's DM sat unread in belam's INTERACTIVE prime session, not in a dispatched sub-agent. Registering the hook globally or project-scoped right now would show every interactive director/quorum seat 'unknown's mail (whatever cursor state that resolves to) rather than their own -- not just unhelpful, actively misleading (false-clean or false-alarm depending on what unknown happens to hold). DID NOT REGISTER. Created then removed an unstaged .claude/settings.json entry rather than ship this. WHAT'S NEEDED: a way for an interactive session to durably know its own seat name that a fresh bash hook invocation can read without trusting the tmux window name outright. Candidate: the seat pin file each director already writes at session start (rotate.py meter --seat <name> --pin .agi/sessions/<name>.meter) durably associates a transcript with a seat name -- if a hook can learn the CURRENT transcript path (check whether CC exports something like a session-id env var to hooks) it could cross-reference against every .meter pin file to find whose session this is, same trust model as the existing pin mechanism, not a new one. Not investigated further -- next round's job. Everything else about the build stands: dm+room+inbox unified (constraint 5), no polling, system-reminder-tagged (constraint 3), alerted_at recorded (constraint 4), 7+2163 tests green. CORRECTION, 2026-09-08 12:5xZ, added by belam-S1-L3-XIII: THE "SUPPORTING RESEARCH" PARAGRAPH IN THIS BODY IS WRONG AND MUST NOT BE BUILT AGAINST. It records, as investigated and settled, that cross-session PUSH is impossible: that SendMessage is usable only from within a live agent turn, that the messaging socket a session exports is scoped to its own hooks and children, and that therefore "no CLI or hook path exists to push a message into an arbitrary other session" -- concluding that a PULL hook is the right shape INSTEAD OF a cross-session PUSH. The investigation was careful and the conclusion is false.

DISPROVEN LIVE, IN BOTH DIRECTIONS, TODAY. Claude Code's own cross-session messaging carried messages between independent sessions on this host repeatedly during the 06:25Z-12:34Z incident: prime to seat, seat to prime, seat to seat, every one delivered while the recipient was mid-turn. It is not a theoretical capability. It was the ONLY thing that reached `sanctuary-director` and `self-perpetuating-II`, two seats born AFTER every file-DM was written and therefore holding no file-DM identity at all -- .agi/comms could not have reached them by any route. It is what contained the incident.

THE OWNER HAS SINCE INSTRUCTED IT DIRECTLY, verbatim via the liaison: "use SendMessage (or whatever works) to reach any seat directly, not just file-DM -- all Claude models on one host, comms aren't unified yet." Recorded as HANDOFF section 6 item 69.

THE SHAPE TO BUILD, `sanctuary-master`'s words and the right answer: "send.py should write the file-DM as it already does AND fire a SendMessage as the alert, one mechanism, record plus notification, not two channels." The file is the RECORD, which satisfies the owner's constraint 4 -- "I never got it" and "I ignored it" must stay distinguishable failures, and a socket send alone leaves no trace. The cross-session send is the NOTIFICATION, which satisfies constraints 1, 2 and 3 -- no agent-side polling, survives the recipient being mid-turn (measured, every send today landed on a busy target), and distinguishable from the owner speaking (it arrives tagged as a peer message, not as user input). That is four of five satisfied by the transport and the fifth by the file, with ONE mechanism, which is constraint 5. The PULL hook this node designed is not wrong and may still be worth having for the cold-start case; it is simply not the only option, and it was chosen on the strength of a negative result that does not hold.

ONE HAZARD THAT MUST RIDE WITH THE FIX, measured today: cross-session names are OPAQUE AND NOT UNIQUE. `agi-32` resolved to three different sessions (liaison, all-is-one, and a 22-hour-old shell) and `agi-9d` to two (self-perpetuating, alive). A bare-name send silently reaches the wrong seat -- the same defect family as the seat-pin collisions, in a new place. Address by an unambiguous reference, never a bare name, and put the seat-to-session mapping in the seat registry as a `session_ref` field rather than reconstructing it by hand through tmux window ids, which is what `sanctuary-master` had to do to talk to a newborn seat at all. That field is being built by `sanctuary-director` alongside the `worktree` field.
