# hypothesis:a00-4a21983b-0f342a

## Hypothesis

**A capability provider can add optional pane operations to the existing Grok adapter module without turning pane support into a required harness interface or a Grok-specific branch.**

The current adapter loader returns a module namespace as the adapter object. A later implementation may therefore inject one generic pane-capability provider into that namespace. `pane_attach`, `pane_send`, and `pane_read` should delegate to that provider; when no provider or named pane hold is available, they should raise the existing named adapter error immediately. Durable hold creation and lifetime remain owned by `goal:g7.31.1`.

### Prove

1. A focused test injects one fake provider through the generic capability seam and calls all three operations through `adapters.load("grok_bot")`; the same object still passes every required g7.25 method.
2. A fixture with no provider, and one with a provider but no named pane, each fail immediately with a named error naming the unavailable capability or pane.
3. The provider test mutates no global dispatch/rotate path and requires no second Grok adapter module.
4. The existing `test_dispatch_still_has_zero_grok_hits` remains green.

### Disprove

The design is disproved if generic capability injection requires a `grok` name branch, enlarges `adapters.REQUIRED`, creates/owns the durable hold behind the adapter, silently falls back to an anonymous pane, or cannot produce a stable named failure for each missing precondition.

## Scope

This narrows the unimplemented claim left by `experiment:a00-828a89b3-8a325b`: it is about the **adapter-to-capability seam**, not pane messaging semantics (`goal:g7.32.2`) or transport routing (`goal:g7.32.4`).
