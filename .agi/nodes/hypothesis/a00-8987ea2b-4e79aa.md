# No message daemon on the heal/cron surface: a reproducible absence-check

## Claim

**Falsifier 1 of `goal:g7.31.4.3`:** no new message daemon process appears in
the heal/cron surface. The claim is an ABSENCE, checked by a reproducible,
falsifiable inventory at
`extensions/agi/tests/test_no_message_daemon_heal_cron.py`.

## The check (data in, findings out)

Three surfaces, each a pure function that takes the data as a PARAMETER so a
caller can feed a declaration that DOES contain a message daemon and see it
flagged BY NAME:

1. `message_job_findings(jobs)` — `mail_poll`/`nudge_sweep` must be periodic
   ticks (`every_mins`/`schedule`); any message-flavoured job outside the
   closed set, or any `KNOWN_JOBS` name that is itself a daemon/router, is a
   finding.
2. `message_service_findings(services)` + `service_allowlist_findings(...)` —
   a systemd unit is long-running by construction, so any message token in its
   name or exec argv is a daemon; any service outside the reviewed
   non-message allowlist is surfaced.
3. `find_message_daemon_processes(procs)` — takes an injectable
   `(pid, comm, args)` table, matches *program-identity tokens* (basenames of
   the first few argv tokens), never a substring of the whole argv. `ps`
   appears only in `read_process_table`, never in the scanner.

## Falsifiability (the negative probe)

The `test_falsifier_*` tests feed synthetic data and assert the checker fires:
a `message-router` service is flagged by name; a `mail_poll` with no schedule
is flagged; an out-of-set `message_daemon` job is flagged; a
`message-router --serve` process is flagged; a clean synthetic table produces
no findings. Same pytest command — all 9 pass.

Measured before the token filter: a naive substring scan of `ps args` reports
every running agent as a message daemon, because the system prompt in argv
contains both "message" and "daemon". Matching program-identity tokens
(basename of the first few argv tokens) removes that false positive; the live
scan above is the after.

## Verdict rationale

The absence holds at this tip: the crons node declares no message service,
both message jobs are periodic ticks, and the live process table contains no
message daemon. An absence cannot be proved absolutely from a single tip, so
the honest verdict is `inconclusive_lean_proved` at high confidence, not
`proved`.
