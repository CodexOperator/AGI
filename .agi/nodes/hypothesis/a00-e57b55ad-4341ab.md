# Optional pane operations can remain an extension of the single Grok adapter

## Claim

The existing `grok_bot_adapter` can expose pane operations through one optional adapter capability—without a second adapter module, dispatch/rotate special cases, or re-implementing durable pane ownership.

## Test

A small contract probe should discover `pane_attach`, `pane_send`, and `pane_read` on one adapter object, then verify both paths:

1. **Pane-capable adapter:** calls operate on the pane held by the adapter.
2. **Ordinary adapter:** these attributes may be absent, and direct invocation of a present method with no held pane raises a named error rather than hanging.

A second probe should inspect the import graph and `dispatch.py` / `rotate.py` for a new Grok-specific branch or a second pane adapter module.

## Predicted evidence

The contract probe passes both paths with unchanged `build_command`; the import-graph probe finds no new parallel adapter and no harness-name branch in dispatch/rotate.

## Falsifier

The claim is false if pane operations require a second adapter module, if a non-pane harness is forced to implement pane semantics, if missing-hold invocation hangs or fails without a named error, or if dispatch/rotate gains Grok-specific policy.

## Scope

This is a hypothesis about adapter shape and failure behavior. It does not define message semantics, session ingest, routing policy, or the durable hold itself; those belong to sibling goals and `goal:g7.31.1`.
