# hypothesis:a00-e2428b1f-985900

## Claim

The default held-seat restart path must build the adapter's `child_env` before
returning and pass that environment through the tmux respawn/reattach seam. A
credential-none harness must therefore lose `OPENROUTER_API_KEY` on restart,
while a default harness keeps it.

## Probe and result

I searched the production tree for the named `tmux_hold` seam and found no
`tmux_hold.py` or equivalent `HOLD_PANE` implementation; the only present
restart supervision is `_supervise_persistent`, whose `reopen` closure is
opaque and whose tests cover adapter restart, not a held tmux pane. The focused
credential regression suite passes (`12 passed`), so it proves the existing
adapter restart rule but does **not** prove the held restart target state.

## Falsifier

The claim is disproved on this checkout because the required hold seam is
absent, and therefore there is no observed env handoff for that path to carry.
A follow-up must first locate or create the hold implementation, then add a
probe that captures the env supplied to tmux respawn/reattach and assert the
credential-none key is absent.
