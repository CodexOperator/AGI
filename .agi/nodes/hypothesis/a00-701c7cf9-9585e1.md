# hypothesis:a00-701c7cf9-9585e1


## Hypothesis

A message sent by a **harness seat whose pane does not render the Claude
`❯` prompt glyph** (a grok-bot pane, or any other) through the `send.py`
seam lands in the recipient inbox **and** a wake-token nudge is typed into
the recipient pane -- **with no harness-name branch anywhere in the
transport**. The box glyph is data on the recipient's own
`config:posts`/`config:seats` row (a `prompt_marker` cell, string or list);
absent means the Claude default and byte-identical behaviour.

## What proves it

An engine test that builds a hermetic tmp project with a sender row carrying
`harness: grok-bot` and a recipient row carrying a non-`❯` `prompt_marker`,
fakes tmux with a pane whose box glyph is that marker, runs the real
`send.send(...)` seam, and asserts (a) one inbox block from the grok seat,
byte-exact body; (b) one `tmux send-keys -l -t <target> <token>` call plus a
separate `Enter` call; (c) the typed string equals `_build_nudge_token` and
carries no body.

## What disproves it

The nudge does not fire on the non-`❯` pane, or fires only by branching on a
harness NAME, or the fix types into an unrecognized box (defeating the
SHAPE-A safety that a box the engine cannot find is never typed into).

## The line that must not move

A non-`❯` box with **no** `prompt_marker` cell stays unrecognized: the
coalesce reason is `"no rendered box"` and nothing is typed. The marker is
data on a row, never a guessed glyph.

## Agent Notes
Grok-pane outbound built: box glyph travels as a row-carried prompt_marker (no harness branch); 2-test file proves inbox+nudge on a non-❯ pane and preserves SHAPE-A (unmarked non-❯ box still 'no rendered box'); 355 sibling tests green; 32 net production lines.
