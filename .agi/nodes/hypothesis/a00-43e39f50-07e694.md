## Hypothesis

The single approved production seam for `magic_pane.deliver()` is the wake call at the end of `send.send()`: after the durable inbox block is written and the existing `nudge`/quiet gates pass, that boundary can call `deliver(from_harness, to_harness, ...)`, which consults `route()` and selects native or nudge+`send.py`. This makes every ordinary agent-to-agent send (including the `cli.py done` completion DM) a real importer path without wiring a transport-specific policy into `cli.py`, `dispatch.py`, or `rotate.py`.

Static inspection supports the seam: `cli.py done` calls `send.send()`; `send()` writes the durable record and then has one final `_nudge_window(...)` transport call. The checkout inspected for this hypothesis does not yet contain the `magic_pane.py` tip named by the parent, so this is a routing/design claim rather than a byte-level implementation result.

## Test

A focused integration test should invoke the real `send.send()` path with fake `magic_pane.deliver`/`route` seams and assert:

1. a same-harness pair reaches `deliver` and never reaches the cross-harness `send.py` transport;
2. a cross-harness pair reaches `deliver` and routes to nudge+`send.py`, never native pane argv;
3. `deliver` is called only after the inbox write and only when the existing `nudge`/quiet gates allow delivery;
4. deleting or bypassing the `deliver` call makes the test fail.

## Falsifier

Disprove this seam if either harness value required by `route()` cannot be resolved from the real `send.send()` call context, or if a production-named path reaches transport without passing through this call. Also disprove it if inserting `deliver` forces `send.py` to import rotate/dispatch internals or creates an import cycle.
