# verdict:a00-fab74146-0b8e47

## Verdict

**Inconclusive, leaning disproved (80%).** The experiment substantially built
the named seam, but it does not yet satisfy the held-pane invariant in a
production-compatible way on the most important completion branch.

## Evidence

The experiment node is the evidence run. Its focused suite reports 24 passing
tests and verifies that production first spawn reaches `tmux_hold.start_or_popen`,
records a stable pane id, and preserves direct-`Popen` fallback. Those results
support the architectural direction of the hypothesis.

The same experiment records the decisive production-level falsifier: for a
successful held child (`hold.done=0`), `HeldProcess.poll()` returns `0`, but
`dispatch.py` then reads `proc.returncode`. `HeldProcess` has no `returncode`
member, so the call raises `AttributeError` at the production dispatch
compatibility point. The mocked tests omit this fast-successful-exit branch.
Thus the named seam exists and restart/fallback wiring is present, yet a
successful first launch crashes during the post-start handling rather than
returning its return code.

This is not a full disproval: the hypothesis explicitly predicts convergence on
one hold record, and the experiment demonstrates most of that convergence. It
is not a proof: the central fast-success path is broken, and the exact proposed
falsifier list did not name this compatibility requirement. The next
implementation child should add `HeldProcess.returncode`, test production startup
with an `rc=0` child, and consider cleanup of partial tmux/session state.
